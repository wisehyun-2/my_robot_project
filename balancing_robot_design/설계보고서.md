# 자가균형 로봇 설계 보고서 — ROS 2 + Teensy, 직접구동(Direct-Drive) 휠

작성일 2026-10-20. 대상: 1번 레퍼런스(Ryung-coding IONIA)의 부품 구성 + DIABLO(DDTRobot) 아키텍처를 참고해 만드는 2륜 자가균형 로봇.
모든 수치 계산은 `sim/` 폴더의 스크립트로 재현 가능하며, 결과 원본은 `results/*.json`, 그림은 `figures/`에 있다.

## 0. 요약 (먼저 읽을 것)

| 질문 | 결론 |
|---|---|
| **1번 프로젝트 문제의 "상당수"가 균형 루프를 ROS 2에서 돌린 탓인가?** | **부분적으로만 사실.** 저자들이 기록한 문제 중 ROS 2/지연을 지목한 것은 하나도 없다. 코드를 보면 (a) 바퀴 속도 피드백이 아예 닫혀 있지 않고, (b) ODrive를 **속도 모드**로 쓰며, (c) 모터 명령이 Python 노드의 USB 동기 왕복 6회를 거치고, (d) IMU도 Python/pyserial을 거친다. 시뮬레이션상 이 구조는 지연과 무관하게 드리프트/불안정하고, I/O 경로 지연(추정 20–50 ms)은 안정 한계(30–40 ms) 근처다. 즉 원인은 "ROS 2 실행기"가 아니라 **제어 구조 + Python I/O 경로 지연 + 속도 모드**다. ROS 2 C++ 노드 100 Hz 자체의 오버헤드는 0.2 ms 수준이다. |
| **균형 루프를 MCU로 옮기는 것이 맞나?** | **맞다.** 다만 이유는 "ROS 2가 100 Hz를 못 돌려서"가 아니라 결정성(지터 µs), 센서→토크 지연 1–2 ms 확보, PC/ROS가 죽어도 서 있는 안전성(DIABLO·PX4·Segway 방식)이다. Ascento(NUC 400 Hz), Ollie(PC 1 kHz)처럼 PC에서도 가능하지만 C++·CAN·RT 커널이 전제다. |
| **어떤 제어기를 쓸 것인가?** | **LQR + 속도 적분(LQI), Teensy 4.1에서 1 kHz(최소 500 Hz), 토크(전류) 모드.** 계산 결과: 캐스케이드 PID는 수식상 상태 피드백의 부분집합이라 같은 게인이면 성능이 동일하고(그림 겹침), LQR은 그 게인을 모델에서 바로 얻는다. MPC는 회복 가능 틸트(40°)·푸시(100 N) 모두 LQR과 **동일**했고, 속도 제한 상황도 "LQR + 레퍼런스 클리핑/램프"가 MPC와 동급이었다. MPC는 Teensy에서 2–8 ms/solve라 100 Hz는 가능하나 1 kHz는 불가 → 2단계(휠-레그, 명시적 제약)로 미룬다. DIABLO도 LQR(8상태, 적분 포함)이다. |
| **직접구동 하드웨어 (5–10 kg, DDT 제품 제외)** | 24 V 6S, **MyActuator RMD-L-9015-35T**(1.67 Nm 연속/5 Nm 최대, Kt 0.45, 650 g, CAN 1 Mbps 전류 지령, 14-bit 엔코더, $219) ×2를 5 kg·10 kg 공통 1순위. 5 kg 경량화면 RMD-L-7015(360 g), 10 kg 연속토크 여유면 RMD-L-9025, 최저가·최대토크면 호버보드 허브 + ODrive S1 + 외부 엔코더, 직접구동 포기 시 CyberGear. Teensy 4.1 + CAN(FD) 트랜시버 + ICM-42688-P(SPI) → CAN 토크 명령 1 kHz, UART 460800으로 PC(ROS 2)와 100 Hz 텔레메트리/50–100 Hz 명령. |

산출물: 설계 보고서(이 문서), 동역학 모델·제어기 비교 시뮬레이션(`sim/`), 게인 생성기(`sim/gen_gains.py`), Teensy 균형 루프 스켈레톤(`firmware/teensy_balance/teensy_balance.ino`), 그림 6장.

**(c) 이 로봇 모델로 직접 계산한 지연 허용치** (`sim/analysis_controllers.py`, `figures/stability_map_rate_vs_latency.png`)

세 파라미터 세트(1번 로봇 유사 / 계획 로봇 / 무거운 로봇)에 대해, 각 루프 주기마다 이산 LQR을 다시 설계하고 센서→토크 총 지연을 바꿔가며 3° 기울임에서 복귀하는지 시뮬레이션했다.

| 로봇 (불안정 극) | 50 Hz | 100 Hz | 200 Hz | 500 Hz | 1 kHz |
|---|---|---|---|---|---|
| 1번 유사(105 mm 휠, 8.2 rad/s) | 30 ms | 30 ms | 30 ms | 30 ms | 30 ms |
| 계획(10 kg, 6.5" 휠, 6.9 rad/s) | 40 ms | 40 ms | 40 ms | 40 ms | 40 ms |
| 무거운(15 kg, 8" 휠, 6.2 rad/s) | 40 ms | 40 ms | 40 ms | 40 ms | 40 ms |

(표의 값 = 복귀에 성공한 최대 총 지연. 위상여유 72°, 교차주파수 29.6 rad/s 설계 → 이론 지연여유 43 ms와 일치.)

핵심: **이 대역폭의 설계에서는 루프 주기(50 Hz–1 kHz)는 거의 무관하고, 총 지연이 30–40 ms를 넘으면 넘어진다.** 더 뻣뻣한(교차 100 rad/s) 설계라면 허용 지연이 10 ms 수준으로 줄어 1 kHz + 저지연이 필요해진다.

같은 모델에서 100 Hz + 15 ms 지연은 1 kHz + 1 ms와 거의 같은 응답(12° 복귀 정착 1.05 s vs 1.05 s)이지만, **100 Hz + 40 ms**는 서 있기는 해도 정착 3.1 s, 토크 RMS 5배, 바퀴 속도 피크 1.15 m/s(0.49 대비)로 크게 흔들린다(`figures/time_response_comparison.png`, 빨간 선).

**(d) 1번 프로젝트의 경로 지연 추정 (측정값 아님, 문헌 수치로 합산)**

IMU 내부 출력 주기(≈10 ms 추정) + USB-시리얼(CP210x 1 ms / FTDI 최대 16 ms) + Python 파싱·DDS(≈1 ms) + 100 Hz 루프 대기(평균 5 ms) + DDS→Python ODrive 노드(USB 6회 왕복: PC 2 ms, ARM 보드 10 ms) + ODrive 속도 루프(Hall 센서, 수십 ms 응답) ≈ **20–50 ms**. 안정 한계(30 ms) 근처라 "흔들리며 서 있는" 상태와 부합한다.

**(e) 그러나 구조적 문제가 더 크다** (`results/velocity_mode_latency_tolerance.json`)

1번 로봇 모델로 "속도 모드 + 바깥 PD(θ)" 구조를 시뮬레이션하면:

| 구조 | 100 Hz 허용 지연 | 500 Hz 허용 지연 |
|---|---|---|
| 토크 모드, LQR (직접구동 권장 구조) | 30 ms | 30 ms |
| 속도 모드, 드라이버 P 루프만 + 바깥 PD(θ) **+ 바퀴속도 피드백** | 40 ms | 40 ms |
| 속도 모드, 드라이버 **PI** 루프(ODrive 기본) + 바깥 PD(θ)만 (**1번 구조**) | 불안정 (지연 0에서도) | 불안정 |
| 속도 모드, P 루프 + 바깥 PD(θ)만 (바퀴 피드백 없음) | 불안정 | 불안정 |

이유(수식): 드라이버 속도 루프 τ = Kp_v(ω_ref − ω)는 토크 모드로 환산하면 바퀴 속도에 **음의 피드백**(−Kp_v/r)을 거는 것인데, 균형에는 바퀴 속도에 **양의 피드백**(LQR의 k_v > 0 항)이 필요하다. 바깥 루프가 바퀴 속도를 되먹이지 않으면 이를 상쇄할 수 없고, 적분기가 있으면 정상상태에서 토크가 θ에 의존하지 않게 되어 복원력 자체가 사라진다. 토크 모드 캐스케이드라도 바퀴 피드백이 없으면 각도는 잡히지만 속도가 0.3–0.5 m/s로 드리프트한 채 돌아오지 않는다(그림의 갈색 선).

**결론:** "1번의 문제 상당수가 ROS 2에서 균형 루프를 돌린 데서 왔다"는 **근거 없는 과장**이다. 근거 있는 원인은 (1) 바퀴 속도 피드백 누락·토픽 불일치·한쪽 바퀴만 구동, (2) ODrive 속도 모드 + 적분기, (3) Python I/O 경로(pyserial IMU, USB ODrive 6회 왕복)의 20–50 ms 지연, (4) Hall 센서 속도 추정이다. (3)은 MCU+CAN으로 옮기면 1–2 ms로 사라지므로 **이전 결정은 옳지만**, (1)(2)(4)는 Teensy로 옮겨도 그대로 재현된다. 이 보고서의 제어기·하드웨어 설계는 이 네 가지를 모두 제거하는 것을 목표로 한다.

## 4. 제어기 선택 — 조사·계산·판단

### 4.1 모델

상태 x = [x_w, ẋ_w, θ, θ̇], 입력 τ = τ_L + τ_R (직접구동이라 모터 토크 = 바퀴 토크).

```
a11 ẍ + a12 θ̈ − M_b l sinθ θ̇² + b ẋ = τ / r
a21 ẍ + a22 θ̈ − M_b g l sinθ        = −τ
a11 = M_b + 2m_w + 2I_w/r²,  a12 = a21 = M_b l cosθ,  a22 = I_b + M_b l²
```
선형화(θ≈0)하면 Ẋ = AX + Bτ. 계획 로봇의 열린 루프 극: +6.88, −6.9, 0, −0.05 rad/s → **불안정 시정수 145 ms**. 제어기는 이보다 3–5배 빠른 교차주파수(20–35 rad/s)가 필요하고, 그 교차주파수에서의 위상여유가 허용 지연을 결정한다. 요(ψ) 축은 분리되어 I_z ψ̈ = (τ_R − τ_L)·d/(2r).

### 4.2 후보 비교

| 기준 | 캐스케이드 PID (각도 PD + 속도 PI) | **LQR / LQI** | 선형 MPC |

→ 평범한 2륜 균형(다리 없음)에서는 **회복 한계가 물리(토크·속도)로 정해지고 MPC가 그 한계를 넓히지 못한다.** 속도 제한도 LQR에 레퍼런스 클리핑·램프를 붙이는 것으로 MPC와 동급 이상이다. MPC가 값어치를 하는 곳은 (1) 휠-레그에서 높이·점프·접촉 제약, (2) 토크-속도 포락선을 **명시적으로** 지켜야 하는 고속 주행, (3) PC에서 100 Hz로 레퍼런스(ẋ_ref, θ_ref)를 생성하고 MCU LQR이 1 kHz로 추종하는 계층 구조다.

### 4.4 판단

**Teensy 4.1에서 1 kHz(최소 500 Hz) LQI, 토크 모드.** 요 축은 자이로 요레이트 PD. 다리를 달면 DIABLO처럼 상태를 늘리고(γ, 높이) 높이는 PD+FF, 게인은 높이별 스케줄링. MPC는 2단계에서 PC(100 Hz) 레퍼런스 생성기 또는 TinyMPC로 실험.

근거 요약: (1) 수식상 PID 캐스케이드 ⊂ 상태 피드백이므로 PID를 고를 이유가 "익숙함"뿐이고, 1번 프로젝트의 실패(부호·피드백 누락)는 정확히 손 튜닝의 함정이었다. (2) LQR은 5개 곱셈이라 MCU 1 kHz에 비용이 없고, 지연여유 43 ms 설계가 MCU+CAN 경로(1–2 ms)에서 20배 여유를 갖는다. (3) MPC는 측정 가능한 이득이 없고 Teensy에서 100 Hz가 한계다. (4) DIABLO(상용)와 Ascento(학술) 모두 LQR이다.

### 4.5 구현 사양 (펌웨어 `firmware/teensy_balance/teensy_balance.ino`)

| 블록 | 사양 |
|---|---|
| 타이밍 | `IntervalTimer` 1 kHz ISR이 플래그만 세우고 메인 루프에서 IMU 읽기→추정→LQI→CAN 송신. CAN 수신·UART 파싱은 비차단 |
| 추정기 | 상보필터 θ = α(θ + g_y Δt) + (1−α)·atan2(a_x, a_z), α = τ/(τ+Δt), τ = 0.5 s. θ̇는 자이로 직접 사용(수치미분 금지). 바퀴 속도는 드라이버 엔코더 피드백 평균 × r. 2단계: 자이로 바이어스 포함 칼만 |
| 제어 법칙 | u = −(K_V(ẋ−v_ref) + K_TH θ + K_THD θ̇ + K_I z), z = ∫(ẋ−v_ref)dt, |z| ≤ 1 m(안티와인드업). τ_L = u/2 − τ_yaw/2, τ_R = u/2 + τ_yaw/2, τ_yaw = Kp_yaw(ψ̇_ref − ψ̇) |
| 레퍼런스 | v_ref 램프 1 m/s², |v_ref| ≤ 0.7×무부하 속도 |
| 안전 | |θ| > 34° → FAULT(토크 0); 명령 0.5 s 없음 → v_ref = 0; 2 s → OFF; 드라이버 피드백 50 ms 없음 → FAULT; 토크 리밋 τ_max; 암(arm)은 |θ| < 3°일 때만 |
| 모터 어댑터 | Iq = τ/Kt를 CAN으로. MyActuator RMD-L(0xA1 토크 지령, 응답이 피드백), moteus(위치 모드 Kp=Kd=0 + feedforward torque), ODrive(`Set_Input_Torque` 0x00E + 워치독) 중 택일 |

부호 규약: θ > 0 = 앞으로 기욺, ẋ > 0 = 전진, τ > 0 = 바퀴를 앞으로 미는 모터 토크. 게인이 모두 음수이고 u = −Kx이므로 **앞으로 기울면 앞으로 밀고, 앞으로 가고 있으면 더 앞으로 민다**(양의 바퀴속도 피드백). 이 부호가 손 튜닝에서 가장 자주 틀리는 부분이다.

### 4.6 튜닝·검증 절차

1. **파라미터 측정**: 총질량, 휠 질량, r, 무게중심 높이 l(축에서 매달아 평형점), I_b(양방향 진자 주기법), 모터 Kt(매달고 전류 vs 토크). → `gen_gains.py`에 입력.
2. **드라이버 단독**: 토크 모드에서 전류 명령 → 토크 부호·스케일 확인, 엔코더 속도 부호 확인, CAN 1 kHz 왕복 확인(Teensy에서 피드백 타임스탬프 통계).
3. **IMU 단독**: 축 정렬, 정지 노이즈(θ̇ 0.1 °/s급), 상보필터 시정수.
4. **매달기 테스트**: 바퀴가 공중에 뜬 상태에서 몸체를 기울이면 바퀴가 "넘어지는 쪽"으로 가속하는지(부호 검증), 지면 없이 토크 리밋 확인.
5. **저게인 착지**: 게인을 0.5배로 시작해 서 있으면 1.0배. 진동(≈ 교차주파수 5 Hz 근처)이 보이면 지연/필터 지연 확인(위상여유 소비).
6. **푸시·경사·속도 스텝** 로그를 rosbag으로 남기고 시뮬레이션과 비교해 모델 파라미터 보정.

흔한 실패 체크리스트: IMU 축/부호, rev/s vs rad/s, Kt의 RMS/peak 규약, 엔코더 방향, 좌우 모터 회전 방향 반전, CAN 종단 저항, 속도 모드로 잘못 설정된 드라이버, 적분 와인드업, 레퍼런스 램프 누락, 100 Hz 로그 출력으로 인한 지터.
