# 오픈소스 휠-레그 균형 제어기 전수 조사 및 SIL 비교 보고서

작성일 2026-10-20. 대상: 고관절 모터 2개(다리당 1개) + 바퀴 2개, Ascento형 4-모터 로봇. 모든 수치는 `sil/` 하네스로 재현 가능하다(`python3 sil/sil_harness.py --robot small|large`).

---

## 0. 요약

- GitHub 전수 조사에서 실제 균형 제어 코드가 있는 휠-레그 저장소 45개를 분류했고, **고관절 2 + 바퀴 2(Ascento형)이면서 제어 법칙을 소스에서 확인한 것은 9개**(fern, LZU_ASCENTO, zephyr_ascento, Pow_WBR, MuShibo, WL1, Venus-1, SonicRobot, Ryung). Ascento 원본·SK8O·DIABLO·TITA는 균형 코드 비공개.
- 9개 전부의 균형 제어 함수를 **C로 그대로 이식해 컴파일**하고, 내 제어기(1 kHz LQI, C 안에서 리카티를 풀어 다리 길이별 게인 자동 설계)와 같은 비선형 시뮬레이터·같은 외란·같은 노이즈·같은 다리 변화에서 5 kg급·10 kg급 두 로봇으로 비교했다.
- **결과**: LQR 계열 5개(내 LQI, fern, LZU, zephyr, Pow)만 두 로봇 모두에서 균형·다리 변화를 통과했다. 손튜닝 캐스케이드 PID(WL1, Venus-1)는 어떤 출력 스케일에서도 균형 불가, MuShibo는 한계 진동, 속도 모드+바퀴 피드백 없음(SonicRobot, Ryung)은 푸시 뒤 굴러간다. 내 LQI는 속도 스텝(정상상태 오차 0, 변위 0), 10° 복귀 0.8~1.0 s, 다리 1.4배 변화 0.1° 흔들림으로 동급 이상이며, fern 구조에 내 가중치를 넣으면 같은 성능이 나온다(차이는 구조가 아니라 가중치).
- **upkie(6모터)**도 같은 절차로 테스트했다(§6). 실제 로봇용 WheelBalancer, 실제 Python MPC 코드(qpmpc+ProxQP)까지 루프에 넣었다. 전부 moteus 속도 모드에 기대는 구조라 드라이버 루프가 무르면 넘어지고, 우리 로봇에서는 푸시 10~40 N(내 LQI 60~120 N)에 그친다. MPC는 가장 조용하지만 느리다. 균형 법칙보다 소프트웨어 구조(스파인/에이전트 분리, 관측기, 시뮬 환경)를 참고할 가치가 있다.
- **결론**: 제어기는 내 LQI를 쓰고, 참고 프로젝트에서는 속도 필터(LZU/zephyr), 중력 피드포워드·균형점 트림(fern/MuShibo), 워치독·바퀴 이탈 감지(fern/MuShibo)만 가져온다. 상세는 §5.4.

## 2. 테스트 방법 — SIL(software-in-the-loop) 하네스

각 프로젝트의 **균형 제어 함수를 C로 그대로 옮겨 gcc로 컴파일**(.so)하고, Python 비선형 2륜 역진자 모델(`sim/twip_model.py`)에 ctypes로 연결했다. 제어기 소스의 게인·루프 주기·필터·제한값·구조를 바꾸지 않았고, 다른 로봇에서 돌리기 위해 바꿀 수밖에 없는 것만 바꿨다.

| 항목 | 처리 |
|---|---|
| 단위 | 각 프로젝트가 쓰는 단위(deg, rad, rpm, 엔코더 count)로 변환해서 입력 |
| 출력 스케일 | 전압/PWM/전류 카운트 출력 프로젝트는 출력→토크 변환 계수가 로봇마다 다르므로, **게인 비율은 유지한 채 전체 스케일 하나만** 로그 범위로 탐색해 최적값 사용(가장 유리한 조건) |
| 부호 | 선형 제어기는 입출력 전체 부호 반전에 대칭이므로 양쪽 부호 중 균형이 잡히는 쪽 사용 |
| 속도 모드 출력(ODrive 등) | 드라이버 속도 루프(PI + 속도 측정 LPF)를 하네스가 모사. Ryung·SonicRobot은 ODrive 기본 게인 범위에서 가장 유리한 값 사용 |
| 기계 영점 | 각 로봇의 무게중심 보정 상수(예: Ryung +0.1164 rad, LZU φ_set, zephyr θ_eq 0.315)는 0으로 설정(시뮬레이션 평형이 θ = 0) |
| 다리 길이 | 하네스가 다리 길이(무게중심 높이 l)를 바꾸면 해당 프로젝트의 게인 스케줄(다항식·테이블)에 그대로 전달 |
| 미이식 요소 | zephyr의 정지마찰 보상(전류→토크 상수 미공개), LZU의 바퀴 이탈 감지, MuShibo의 점프 상태기, fern의 트림 학습·고관절 FF1 |

벤치마크(모두 센서→토크 지연 2 ms, 프로젝트 고유 루프 주기, IMU 노이즈 0.2°/0.5°/s rms, 엔코더 양자화 포함):

| 항목 | 정의 |
|---|---|
| 최대 복귀 틸트 | 정지 상태에서 초기 기울기 θ0를 2.5° 간격으로 올려 3° 이내로 정착하는 최대값(상한 40°) |
| 최대 푸시 | 무게중심에 0.1 s 동안 수평력 F를 가해 정착하는 최대값(상한 160 N) |
| 속도 스텝 | 0.8 m/s 계단 명령(0.5→3.0 s): 90 % 상승시간, 오버슈트, 최대 기울기 |
| 지연 허용치 | 3° 기울기에서 복귀하는 최대 센서→토크 지연 |
| 다리 길이 변화 | 균형 중 1 s 동안 다리 길이를 1.4배로 늘렸다 줄임: 안정 여부와 최대 기울기 |
| 정지 떨림 | 노이즈만 있을 때 토크 RMS, 기울기 RMS |

로봇 모델 두 종(가정값): 소형 5 kg급(몸체 3.2 kg, 휠+모터 0.65 kg ×2, r 65 mm, l 0.16 m, 바퀴당 최대 5 Nm), 대형 10 kg급(몸체 7 kg, r 82.5 mm, l 0.25 m, 바퀴당 5 Nm).

## 3. 내가 작성한 제어기 (`sil/controllers/mine_lqi.c`, 펌웨어 `firmware/teensy_balance/`)

- 1 kHz 이산 LQI: 상태 [ẋ − v_ref, θ, θ̇, ∫(ẋ − v_ref)], 토크 출력, 레퍼런스 램프 1 m/s², 안티와인드업, 요레이트 P.
- 게인은 C 코드 안에서 로봇 파라미터로부터 **리카티 반복(Joseph 형식, 배정밀도)으로 직접 계산**하므로 로봇이 바뀌거나 다리 길이가 1 cm 이상 바뀌면 자동 재설계(게인 스케줄링). Python `scipy.solve_discrete_are`와 소수점 셋째 자리까지 일치 확인.
- 가중치 Q = diag(1, 25, 0.25, 1), R = 1/(0.5·τ_max)²: 위상여유 72~77°, 지연여유 31~43 ms.

### 5.3 해석

**(1) 구조가 성패를 가른다.** 모델 기반 전상태 피드백(LQR 계열: 내 LQI, fern, LZU, zephyr, Pow) 다섯 개는 출력 스케일 하나만 맞추면 5 kg·10 kg 로봇 **모두에서** 40° 근처까지 복귀하고 다리 길이 변화에도 안정하다. 손튜닝 캐스케이드 PID(WL1, Venus-1)는 어떤 스케일에서도 균형을 못 잡았고(각도 D 게인이 P 대비 7~10 ms로 너무 작아 관성이 큰 로봇을 감쇠하지 못함), MuShibo의 4항 P는 소토크 PI·균형점 적응이 위상을 갉아먹어 지연 허용 0~5 ms의 한계 진동(limit cycle)을 보인다. 속도 모드 + 바퀴 피드백 없음(SonicRobot, Ryung)은 서 있더라도 푸시 뒤 계속 굴러가고(0.7~0.85 m 이후 가속) 속도 명령을 추종하지 못한다.

**(2) LQR 계열 안에서의 차이는 세 가지다.**
- *속도 상태를 어디에 두는가.* 내 LQI는 속도 오차와 그 적분을 LQR 상태에 넣어 0.8 m/s 스텝을 정상상태 오차 0, 변위 0으로 추종한다. LZU(위치 유지형)는 느리지만 오버슈트 8 %로 가장 부드럽고, Pow(적분 없음)는 밀리면 굴러간다. zephyr는 코드의 속도 항 부호가 LQR 구조와 반대라 균형은 잡아도 속도 추종이 75~90 % 오버슈트·20~28° 기울기로 사실상 불가(문서의 반대 부호는 아예 균형 불가 → 코드 부호가 실제 사용값으로 보임).
- *가중치.* fern의 Q/R(그들 로봇용)을 그대로 쓰면 우리 로봇에선 너무 무르고(복귀 10~15°, 5 kg에서 정착 4.8 s), **같은 구조에 내 가중치를 넣으면 내 제어기와 동급**(40°, 50~160 N, 지연 40~50 ms)이 된다. 즉 fern과 나의 차이는 구조가 아니라 가중치다.
- *바깥 속도 루프의 민감도.* fern 식 "속도 PI → 기울기 목표" 캐스케이드는 PI 게인 0.3/0.6에서 5 kg은 되고 10 kg은 완전히 넘어졌다(0.15/0.3이면 둘 다 됨). LQI는 바깥 루프가 없어 로봇이 바뀌어도 리카티 해만 다시 풀면 된다.

**(3) 내 제어기의 약점 두 가지.** 정지 토크 떨림이 0.098~0.128 Nm RMS로 LQR 계열 중 가장 크다(1 kHz에서 자이로 노이즈에 θ̇ 게인이 그대로 곱해짐; LZU는 10샘플 이동평균으로 0.02). 지연 허용치(30~40 ms)는 더 느리게 튜닝된 LZU·Pow(50~60 ms)보다 작다. 둘 다 Q_θ̇를 줄이거나 자이로에 50 Hz 1차 LPF를 넣으면 해결되며, MCU+CAN 경로(1~2 ms)에서는 여유가 15배 이상이다.

**(4) 최대 푸시의 함정.** 5.2에서 보듯 "더 큰 푸시를 견딘다"가 "더 잘 제어한다"는 뜻이 아니다. 굴러가게 두면 누구나 더 큰 푸시를 견딘다.

### 5.4 결론

1. **균형 제어기는 직접 작성한 LQI(토크 모드, MCU 1 kHz, 온라인 리카티로 다리 길이별 게인 자동 설계)를 기본으로 쓴다.** 조사한 9개 프로젝트의 코드를 그대로 가져다 쓸 이유가 없다. 그들 중 잘 되는 것(fern·LZU·Pow·zephyr)은 모두 같은 LQR 계열이고, 성능 차이는 가중치·속도 상태 처리 차이였으며, 내 LQI가 속도 추종·변위·다리 변화 전 항목에서 동급 이상이다.
2. **참고 프로젝트에서 가져올 것**: LZU/zephyr의 속도 필터(이동평균·13 Hz LPF) → 토크 떨림 저감; fern의 중력 피드포워드(FF2)와 균형점 트림 학습, MuShibo의 균형점 자동 적응 → 기구 무게중심 오프셋 보정; LZU/Pow의 "이동 명령 중 위치 유지 해제"; fern의 워치독·고관절 토크 램프, MuShibo의 바퀴 이탈 감지 → 다리·점프 확장 시.
3. **쓰지 말 것**: ODrive 속도 모드에 바퀴 피드백 없는 PID(SonicRobot, Ryung), 손튜닝 캐스케이드 PID 게인 비율(WL1, Venus-1) — 로봇 질량이 달라지면 전이되지 않는다.
4. **코드 참고 순서**: fern(가장 완성도 높은 Ascento형, MuJoCo 쌍둥이, 500 Hz Teensy) → LZU_ASCENTO(Ascento 4절 기구와 MATLAB K 계산) → zephyr_ascento(파라미터·게인 문서) → Pow_WBR(가장 간결한 높이별 K 테이블).

## 6. upkie (다리당 고관절 + 무릎, 6모터) — 같은 절차로 수행

### 6.1 무엇이 있는가

[upkie/upkie](https://github.com/upkie/upkie) v13.1.0, Apache-2.0, 448★. 다리당 고관절·무릎(mjbots qdd100) + 바퀴(mj5208) = 6모터, 질량 약 5.4 kg, 바퀴 반경 60 mm, 무게중심 높이 약 0.58 m. 균형과 관련된 코드는 네 가지다.

| # | 코드 | 위치 | 구조 | 실행 위치/주기 |
|---|---|---|---|---|
| U1 | **WheelBalancer** (실제 로봇의 기본 균형기) | `upkie/cpp/controllers/WheelBalancer.cpp` | 지면 속도 명령 = −v_target − (0.7·e_x + 1.8·e_pitch) − ∫(1.6·e_x + 20·e_pitch)dt, |v| ≤ 2 m/s → 바퀴 속도 = v/r. 적분기 덕분에 "가속도 PD"와 등가. 비최소위상 트릭(−v_target). 바퀴 이탈 시 적분·목표 위치를 1 s 시정수로 복귀 | 스파인(C++) 1 kHz, moteus **속도 모드** |
| U2 | pd_balancing.py 예제 | `examples/pybullet/pd_balancing.py` | v_cmd = 10·pitch + 1·x + 0.1·ẋ, |v| ≤ 0.99 m/s | 에이전트 1 kHz, 속도 모드 |
| U3 | **MPCBalancer** | `upkie/controllers/mpc_balancer.py` | qpmpc의 운동학적 바퀴 역진자(길이 = 무게중심 높이) 모델, N = 50 × 20 ms, |가속도| ≤ 10 m/s², ProxQP 웜스타트. 첫 가속도를 적분해 지면 속도 명령 | 에이전트 200 Hz(Python), 속도 모드 |
| U4 | torque_balancing.py 예제 | `examples/pybullet/torque_balancing.py` | τ_wheel = 10 Nm/rad · pitch (P만) | 200 Hz, 토크 모드 |

다리(고관절·무릎)는 균형 루프에 들어가지 않고 위치 제어(kp_scale/kd_scale)로 자세만 잡는다. 즉 바퀴 균형 법칙은 4-모터 프로젝트와 같은 층위에서 비교할 수 있다. 그 외 강화학습 밸런서(rl_zoo3_balancer, ppo_balancer)는 별도 저장소라 제외.

### 6.2 이식

- U1·U2·U4는 C로 그대로 이식(`sil/controllers/upkie_*.c`). U1·U2는 지면 속도(m/s) 단위라 로봇에 무관하게 **원본 게인 그대로** 실행했다(스케일 탐색 없음).
- U3는 **upkie의 Python 클래스를 그대로 가져와 루프 안에서 실행**했다(`sil/controllers/upkie_mpc.py`: 복제한 저장소의 `mpc_balancer.py`를 직접 로드, qpmpc 3.2 + proxsuite 0.7 설치, upkie 내부 유틸 3개만 스텁). 모델 길이는 우리 로봇의 무게중심 높이로 설정.
- 세 속도 모드 제어기는 moteus 휠 속도 루프를 하네스가 모사한다. 처음에 썼던 무른 루프(Kp 0.2 Nm/(rad/s))에서는 10 kg 로봇에서 모두 넘어졌고, Kp ≥ 0.5에서 균형을 잡았다. 본 결과는 **뻣뻣한 루프(Kp 1.0, 실제 moteus 수준)** 기준이며, 무른 루프 결과를 함께 표시해 의존도를 보였다.

### 6.4 해석과 결론

1. **upkie의 균형기는 전부 "속도 모드"다.** 토크를 만드는 것은 제어기가 아니라 moteus의 휠 속도 루프이고, 제어기는 지면 속도만 명령한다. 그래서 성능이 드라이버 루프 강성에 직결된다(무른 루프에서 전부 실패). 정지 토크 떨림도 그 결과다. 뻣뻣한 속도 루프가 측정·명령 노이즈를 토크로 바꾸기 때문에 U1 0.16~0.20 Nm, U2 0.9~1.1 Nm RMS로 내 LQI(0.10~0.13)보다 크다. 유일한 예외가 MPC로, 가속도 한계(10 m/s²)가 명령을 매끄럽게 만들어 0.004~0.010 Nm로 가장 조용하다.
2. **게인은 upkie 로봇(무게중심 0.58 m, 불안정 극 4 rad/s)용이다.** 무게중심이 낮아 불안정 극이 7 rad/s인 우리 로봇에서는 U1이 10° 복귀에 토크를 포화시키고도 푸시 10~20 N밖에 못 버티며, 10 kg에서는 속도 스텝에 117 % 오버슈트·18° 기울기를 보인다. U2 예제는 애초에 교육용이고, U4(P만)는 어떤 로봇에서도 설 수 없다.
3. **MPC(실제 코드)는 속도 추종이 가장 매끄럽고 조용하지만 느리고 무르다.** 10° 복귀에 2.7~4.8 s, 40 N 푸시에 0.59 m 밀리거나 넘어진다. 모델이 질량·토크 없는 운동학적 역진자라 외란 복구에 필요한 공격성을 낼 수 없고, Python 200 Hz(ProxQP 웜스타트 1회당 수 ms)는 Teensy에서 돌릴 수 없다.
4. **결론**: upkie의 균형 법칙 자체는 5~10 kg 직접구동·토크 모드 로봇에 가져올 이유가 없다. 내 LQI가 푸시 3~6배, 속도 스텝 오버슈트 절반, 변위 0으로 앞선다. 다만 upkie는 **소프트웨어 구조**에서 참고 가치가 가장 크다. (a) 1 kHz 스파인(C++)과 에이전트(Python)를 공유 메모리로 분리하고 제어기 파이프라인·관측기(바퀴 오도메트리, 바닥 접촉)를 모듈화한 구조는 이 프로젝트의 Teensy/ROS 2 분리와 같은 철학이라 설계 참고가 된다. (b) 바퀴 이탈 시 적분기·목표를 서서히 복귀시키는 "air return" 처리와 MPC의 가속도 한계는 점프·계단 확장 때 가져올 만하다. (c) Apache-2.0에 PyBullet/MuJoCo 환경·RL 베이스라인이 갖춰져 있어 시뮬레이션 쌍둥이를 만들 때 가장 완성도 높은 출발점이다.

## 7. 한계

- 플랜트는 2륜 역진자 + 다리 길이(무게중심 높이) 변화 모델이며 다리 링크 동역학·고관절 토크 결합·타이어 컴플라이언스는 없다. 로봇 파라미터는 가정값.
- 전압/PWM/전류 출력 프로젝트는 스케일 하나만 탐색했다(게인 비율은 그들 값). 비율까지 재튜닝하면 더 잘 될 수 있으나 그러면 "그들의 제어기"가 아니다.
- WL1의 PID 본체, SonicRobot의 엔코더 CPR, zephyr의 정지마찰 전류→토크 상수는 공개 소스에 없어 가정했다. 기계 영점 상수는 모두 0으로 두었다.
- 속도 모드 프로젝트의 드라이버 속도 루프 게인은 ODrive 기본값 범위에서 가장 유리한 값을 골랐고, upkie는 moteus 수준의 뻣뻣한 루프(Kp 1.0 Nm/(rad/s))로 두었다. 실제 moteus 게인은 upkie 설정 파일에 없어 가정값이다.
