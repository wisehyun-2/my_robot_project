# 오픈소스 휠-레그 균형 제어기 전수 조사 및 SIL 비교 보고서

작성일 2026-10-20. 대상: 고관절 모터 2개(다리당 1개) + 바퀴 2개, Ascento형 4-모터 로봇. 모든 수치는 `sil/` 하네스로 재현 가능하다(`python3 sil/sil_harness.py --robot small|large`).

## 0. 요약

- GitHub 전수 조사에서 실제 균형 제어 코드가 있는 휠-레그 저장소 45개를 분류했고, **고관절 2 + 바퀴 2(Ascento형)이면서 제어 법칙을 소스에서 확인한 것은 9개**(fern, LZU_ASCENTO, zephyr_ascento, Pow_WBR, MuShibo, WL1, Venus-1, SonicRobot, Ryung). Ascento 원본·SK8O·DIABLO·TITA는 균형 코드 비공개.
- 9개 전부의 균형 제어 함수를 **C로 그대로 이식해 컴파일**하고, 내 제어기(1 kHz LQI, C 안에서 리카티를 풀어 다리 길이별 게인 자동 설계)와 같은 비선형 시뮬레이터·같은 외란·같은 노이즈·같은 다리 변화에서 5 kg급·10 kg급 두 로봇으로 비교했다.
- **결과**: LQR 계열 5개(내 LQI, fern, LZU, zephyr, Pow)만 두 로봇 모두에서 균형·다리 변화를 통과했다. 손튜닝 캐스케이드 PID(WL1, Venus-1)는 어떤 출력 스케일에서도 균형 불가, MuShibo는 한계 진동, 속도 모드+바퀴 피드백 없음(SonicRobot, Ryung)은 푸시 뒤 굴러간다. 내 LQI는 속도 스텝(정상상태 오차 0, 변위 0), 10° 복귀 0.8–1.0 s, 다리 1.4배 변화 0.1° 흔들림으로 동급 이상이며, fern 구조에 내 가중치를 넣으면 같은 성능이 나온다(차이는 구조가 아니라 가중치).
- **upkie(6모터)**도 같은 절차로 테스트했다(§6). 실제 로봇용 WheelBalancer, 실제 Python MPC 코드(qpmpc+ProxQP)까지 루프에 넣었다. 전부 moteus 속도 모드에 기대는 구조라 드라이버 루프가 무르면 넘어지고, 우리 로봇에서는 푸시 10–40 N(내 LQI 60–120 N)에 그친다. MPC는 가장 조용하지만 느리다. 균형 법칙보다 소프트웨어 구조(스파인/에이전트 분리, 관측기, 시뮬 환경)를 참고할 가치가 있다.
- **6-모터(5절 링크) 프로젝트 10개**(§8)도 같은 절차로 테스트했다. 전부 HEU 3체 모델의 LQR 하나(상태 6, 출력 2)이고, 그 모델로 비선형 플랜트를 만들어 USTB의 공개 게인과 5–10 % 안에서 맞춤을 확인한 뒤 5개 플랜트(RM급 7 kg·Liu 15 kg·Skythinker 0.6 kg·우리 5 kg급·10 kg급)에서 비교했다. 공개 게인은 자기 로봇 질량 근방에서만 그대로 통하고 지연 허용이 3–8 ms(USTB 3 ms)로 Teensy+CAN 구조에는 여유가 없다. 내 LQI6(온라인 리카티, R을 토크 한계에 비례)는 모든 플랜트에서 조정 없이 균형·40° 복귀·1.0–1.2 W 푸시, 지연 26 ms, 정지 토크 노이즈 최저였다. 가져올 것은 USTB의 VMC·파라미터 문서, Skythinker의 다항식 스케줄링, ATWheelLeg의 공중 게인, LJW의 점프 상태기계이지 게인 값이 아니다.
- **결론**: 제어기는 내 LQI를 쓰고, 참고 프로젝트에서는 속도 필터(LZU/zephyr), 중력 피드포워드·균형점 트림(fern/MuShibo), 워치독·바퀴 이탈 감지(fern/MuShibo)만 가져온다. 상세는 §5.4.

## 2. 테스트 방법 — SIL(software-in-the-loop) 하네스

각 프로젝트의 **균형 제어 함수를 C로 그대로 옮겨 gcc로 컴파일**(.so)하고, Python 비선형 2륜 역진자 모델(`sim/twip_model.py`)에 ctypes로 연결했다. 제어기 소스의 게인·루프 주기·필터·제한값·구조를 바꾸지 않았고, 다른 로봇에서 돌리기 위해 바꿀 수밖에 없는 것만 바꿨다.

| 항목 | 처리 |
|---|---|
| 단위 | 각 프로젝트가 쓰는 단위(deg, rad, rpm, 엔코더 count)로 변환해서 입력 |
| 출력 스케일 | 전압/PWM/전류 카운트 출력 프로젝트는 출력→토크 변환 계수가 로봇마다 다르므로, **게인 비율은 유지한 채 전체 스케일 하나만** 로그 범위로 탐색해 최적값 사용(가장 유리한 조건) |
| 부호 | 선형 제어기는 입출력 전체 부호 반전에 대칭이므로 양쪽 부호 중 균형이 잡히는 쪽 사용 |
| 속도 모드 출력(ODrive 등) | 드라이버 속도 루프(PI + 속도 측정 LPF)를 하네스가 모사. Ryung·SonicRobot은 ODrive 기본 게인 범위에서 가장 유리한 값 사용 |
| 기계 영점 | 각 로봇의 무게중심 보정 상수(예: Ryung +0.1164 rad, LZU φ_set, zephyr θ_eq 0.315)는 0으로 설정(시뮬레이션 평형이 θ = 0) |
| 다리 길이 | 하네스가 다리 길이(무게중심 높이 l)를 바꾸면 해당 프로젝트의 게인 스케줄(다항식·테이블)에 그대로 전달 |
| 미이식 요소 | zephyr의 정지마찰 보상(전류→토크 상수 미공개), LZU의 바퀴 이탈 감지, MuShibo의 점프 상태기, fern의 트림 학습·고관절 FF1 |

벤치마크(모두 센서→토크 지연 2 ms, 프로젝트 고유 루프 주기, IMU 노이즈 0.2°/0.5°/s rms, 엔코더 양자화 포함):

| 항목 | 정의 |
|---|---|
| 최대 복귀 틸트 | 정지 상태에서 초기 기울기 θ0를 2.5° 간격으로 올려 3° 이내로 정착하는 최대값(상한 40°) |
| 최대 푸시 | 무게중심에 0.1 s 동안 수평력 F를 가해 정착하는 최대값(상한 160 N) |
| 속도 스텝 | 0.8 m/s 계단 명령(0.5→3.0 s): 90 % 상승시간, 오버슈트, 최대 기울기 |
| 지연 허용치 | 3° 기울기에서 복귀하는 최대 센서→토크 지연 |

## 3. 내가 작성한 제어기 (`sil/controllers/mine_lqi.c`, 펌웨어 `firmware/teensy_balance/`)

- 1 kHz 이산 LQI: 상태 [ẋ − v_ref, θ, θ̇, ∫(ẋ − v_ref)], 토크 출력, 레퍼런스 램프 1 m/s², 안티와인드업, 요레이트 P.
- 게인은 C 코드 안에서 로봇 파라미터로부터 **리카티 반복(Joseph 형식, 배정밀도)으로 직접 계산**하므로 로봇이 바뀌거나 다리 길이가 1 cm 이상 바뀌면 자동 재설계(게인 스케줄링). Python `scipy.solve_discrete_are`와 소수점 셋째 자리까지 일치 확인.
- 가중치 Q = diag(1, 25, 0.25, 1), R = 1/(0.5·τ_max)²: 위상여유 72–77°, 지연여유 31–43 ms.

### 5.3 해석

**(1) 구조가 성패를 가른다.** 모델 기반 전상태 피드백(LQR 계열: 내 LQI, fern, LZU, zephyr, Pow) 다섯 개는 출력 스케일 하나만 맞추면 5 kg·10 kg 로봇 **모두에서** 40° 근처까지 복귀하고 다리 길이 변화에도 안정하다. 손튜닝 캐스케이드 PID(WL1, Venus-1)는 어떤 스케일에서도 균형을 못 잡았고(각도 D 게인이 P 대비 7–10 ms로 너무 작아 관성이 큰 로봇을 감쇠하지 못함), MuShibo의 4항 P는 소토크 PI·균형점 적응이 위상을 갉아먹어 지연 허용 0–5 ms의 한계 진동(limit cycle)을 보인다. 속도 모드 + 바퀴 피드백 없음(SonicRobot, Ryung)은 서 있더라도 푸시 뒤 계속 굴러가고(0.7–0.85 m 이후 가속) 속도 명령을 추종하지 못한다.

**(2) LQR 계열 안에서의 차이는 세 가지다.**
- *속도 상태를 어디에 두는가.* 내 LQI는 속도 오차와 그 적분을 LQR 상태에 넣어 0.8 m/s 스텝을 정상상태 오차 0, 변위 0으로 추종한다. LZU(위치 유지형)는 느리지만 오버슈트 8 %로 가장 부드럽고, Pow(적분 없음)는 밀리면 굴러간다. zephyr는 코드의 속도 항 부호가 LQR 구조와 반대라 균형은 잡아도 속도 추종이 75–90 % 오버슈트·20–28° 기울기로 사실상 불가(문서의 반대 부호는 아예 균형 불가 → 코드 부호가 실제 사용값으로 보임).
- *가중치.* fern의 Q/R(그들 로봇용)을 그대로 쓰면 우리 로봇에선 너무 무르고(복귀 10–15°, 5 kg에서 정착 4.8 s), **같은 구조에 내 가중치를 넣으면 내 제어기와 동급**(40°, 50–160 N, 지연 40–50 ms)이 된다. 즉 fern과 나의 차이는 구조가 아니라 가중치다.
- *바깥 속도 루프의 민감도.* fern 식 "속도 PI → 기울기 목표" 캐스케이드는 PI 게인 0.3/0.6에서 5 kg은 되고 10 kg은 완전히 넘어졌다(0.15/0.3이면 둘 다 됨). LQI는 바깥 루프가 없어 로봇이 바뀌어도 리카티 해만 다시 풀면 된다.

**(3) 내 제어기의 약점 두 가지.** 정지 토크 떨림이 0.098–0.128 Nm RMS로 LQR 계열 중 가장 크다(1 kHz에서 자이로 노이즈에 θ̇ 게인이 그대로 곱해짐; LZU는 10샘플 이동평균으로 0.02). 지연 허용치(30–40 ms)는 더 느리게 튜닝된 LZU·Pow(50–60 ms)보다 작다. 둘 다 Q_θ̇를 줄이거나 자이로에 50 Hz 1차 LPF를 넣으면 해결되며, MCU+CAN 경로(1–2 ms)에서는 여유가 15배 이상이다.

**(4) 최대 푸시의 함정.** 5.2에서 보듯 "더 큰 푸시를 견딘다"가 "더 잘 제어한다"는 뜻이 아니다. 굴러가게 두면 누구나 더 큰 푸시를 견딘다.

### 5.4 결론

1. **균형 제어기는 직접 작성한 LQI(토크 모드, MCU 1 kHz, 온라인 리카티로 다리 길이별 게인 자동 설계)를 기본으로 쓴다.** 조사한 9개 프로젝트의 코드를 그대로 가져다 쓸 이유가 없다. 그들 중 잘 되는 것(fern·LZU·Pow·zephyr)은 모두 같은 LQR 계열이고, 성능 차이는 가중치·속도 상태 처리 차이였으며, 내 LQI가 속도 추종·변위·다리 변화 전 항목에서 동급 이상이다.
2. **참고 프로젝트에서 가져올 것**: LZU/zephyr의 속도 필터(이동평균·13 Hz LPF) → 토크 떨림 저감; fern의 중력 피드포워드(FF2)와 균형점 트림 학습, MuShibo의 균형점 자동 적응 → 기구 무게중심 오프셋 보정; LZU/Pow의 "이동 명령 중 위치 유지 해제"; fern의 워치독·고관절 토크 램프, MuShibo의 바퀴 이탈 감지 → 다리·점프 확장 시.
3. **쓰지 말 것**: ODrive 속도 모드에 바퀴 피드백 없는 PID(SonicRobot, Ryung), 손튜닝 캐스케이드 PID 게인 비율(WL1, Venus-1) — 로봇 질량이 달라지면 전이되지 않는다.
4. **코드 참고 순서**: fern(가장 완성도 높은 Ascento형, MuJoCo 쌍둥이, 500 Hz Teensy) → LZU_ASCENTO(Ascento 4절 기구와 MATLAB K 계산) → zephyr_ascento(파라미터·게인 문서) → Pow_WBR(가장 간결한 높이별 K 테이블).

## 6. upkie (다리당 고관절 + 무릎, 6모터) — 같은 절차로 수행

### 6.1 무엇이 있는가

[upkie/upkie](https://github.com/upkie/upkie) v13.1.0, Apache-2.0, 448★. 다리당 고관절·무릎(mjbots qdd100) + 바퀴(mj5208) = 6모터, 질량 약 5.4 kg, 바퀴 반경 60 mm, 무게중심 높이 약 0.58 m. 균형과 관련된 코드는 네 가지다.

### 6.2 이식

- U1·U2·U4는 C로 그대로 이식(`sil/controllers/upkie_*.c`). U1·U2는 지면 속도(m/s) 단위라 로봇에 무관하게 **원본 게인 그대로** 실행했다(스케일 탐색 없음).
- U3는 **upkie의 Python 클래스를 그대로 가져와 루프 안에서 실행**했다(`sil/controllers/upkie_mpc.py`: 복제한 저장소의 `mpc_balancer.py`를 직접 로드, qpmpc 3.2 + proxsuite 0.7 설치, upkie 내부 유틸 3개만 스텁). 모델 길이는 우리 로봇의 무게중심 높이로 설정.
- 세 속도 모드 제어기는 moteus 휠 속도 루프를 하네스가 모사한다. 처음에 썼던 무른 루프(Kp 0.2 Nm/(rad/s))에서는 10 kg 로봇에서 모두 넘어졌고, Kp ≥ 0.5에서 균형을 잡았다. 본 결과는 **뻣뻣한 루프(Kp 1.0, 실제 moteus 수준)** 기준이며, 무른 루프 결과를 함께 표시해 의존도를 보였다.

### 6.4 해석과 결론

1. **upkie의 균형기는 전부 "속도 모드"다.** 토크를 만드는 것은 제어기가 아니라 moteus의 휠 속도 루프이고, 제어기는 지면 속도만 명령한다. 그래서 성능이 드라이버 루프 강성에 직결된다(무른 루프에서 전부 실패). 정지 토크 떨림도 그 결과다. 뻣뻣한 속도 루프가 측정·명령 노이즈를 토크로 바꾸기 때문에 U1 0.16–0.20 Nm, U2 0.9–1.1 Nm RMS로 내 LQI(0.10–0.13)보다 크다. 유일한 예외가 MPC로, 가속도 한계(10 m/s²)가 명령을 매끄럽게 만들어 0.004–0.010 Nm로 가장 조용하다.
2. **게인은 upkie 로봇(무게중심 0.58 m, 불안정 극 4 rad/s)용이다.** 무게중심이 낮아 불안정 극이 7 rad/s인 우리 로봇에서는 U1이 10° 복귀에 토크를 포화시키고도 푸시 10–20 N밖에 못 버티며, 10 kg에서는 속도 스텝에 117 % 오버슈트·18° 기울기를 보인다. U2 예제는 애초에 교육용이고, U4(P만)는 어떤 로봇에서도 설 수 없다.
3. **MPC(실제 코드)는 속도 추종이 가장 매끄럽고 조용하지만 느리고 무르다.** 10° 복귀에 2.7–4.8 s, 40 N 푸시에 0.59 m 밀리거나 넘어진다. 모델이 질량·토크 없는 운동학적 역진자라 외란 복구에 필요한 공격성을 낼 수 없고, Python 200 Hz(ProxQP 웜스타트 1회당 수 ms)는 Teensy에서 돌릴 수 없다.
4. **결론**: upkie의 균형 법칙 자체는 5–10 kg 직접구동·토크 모드 로봇에 가져올 이유가 없다. 내 LQI가 푸시 3–6배, 속도 스텝 오버슈트 절반, 변위 0으로 앞선다. 다만 upkie는 **소프트웨어 구조**에서 참고 가치가 가장 크다. (a) 1 kHz 스파인(C++)과 에이전트(Python)를 공유 메모리로 분리하고 제어기 파이프라인·관측기(바퀴 오도메트리, 바닥 접촉)를 모듈화한 구조는 이 프로젝트의 Teensy/ROS 2 분리와 같은 철학이라 설계 참고가 된다. (b) 바퀴 이탈 시 적분기·목표를 서서히 복귀시키는 "air return" 처리와 MPC의 가속도 한계는 점프·계단 확장 때 가져올 만하다. (c) Apache-2.0에 PyBullet/MuJoCo 환경·RL 베이스라인이 갖춰져 있어 시뮬레이션 쌍둥이를 만들 때 가장 완성도 높은 출발점이다.

## 7. 한계

- 플랜트는 2륜 역진자 + 다리 길이(무게중심 높이) 변화 모델이며 다리 링크 동역학·고관절 토크 결합·타이어 컴플라이언스는 없다. 로봇 파라미터는 가정값.
- 전압/PWM/전류 출력 프로젝트는 스케일 하나만 탐색했다(게인 비율은 그들 값). 비율까지 재튜닝하면 더 잘 될 수 있으나 그러면 "그들의 제어기"가 아니다.
- WL1의 PID 본체, SonicRobot의 엔코더 CPR, zephyr의 정지마찰 전류→토크 상수는 공개 소스에 없어 가정했다. 기계 영점 상수는 모두 0으로 두었다.
- 속도 모드 프로젝트의 드라이버 속도 루프 게인은 ODrive 기본값 범위에서 가장 유리한 값을 골랐고, upkie는 moteus 수준의 뻣뻣한 루프(Kp 1.0 Nm/(rad/s))로 두었다. 실제 moteus 게인은 upkie 설정 파일에 없어 가정값이다.

## 8. 6-모터(5절 링크, 다리당 관절 2개) 프로젝트 — 같은 절차로 수행

§1.2의 6-모터 프로젝트(현재 접근 가능한 10개 + 이후 비공개로 바뀐 USTB·Multivac 2개) 중 upkie는 §6에서 끝냈고, chen-jiangnan/RMInfantry_wheelLegged_ws는 처음 받은 파일에 게인 값이 없어 제외했다(전체 저장소에는 `chassis_control_config.yaml`에 K가 있음을 뒤에 확인 — `시뮬레이션_환경조사.md` S7, 추후 B11로 추가 가능). 나머지 10개는 **공개된 게인 표·다항식을 그대로** 6-모터 전용 시뮬레이터(`sim6/`)에 넣어 테스트했고, 그중 1772631792/WheelLeg_LQR은 균형 법칙이 다리 각도를 쓰지 않는 4-상태 카트-폴 LQR이라 §5의 4-모터 하네스에 넣었다(B10, §5.1·5.2 표에 행 추가).

### 8.1 이 프로젝트들의 공통 구조

10개 중 9개가 **같은 모델, 같은 제어 법칙**이다. 하얼빈공대(HEU) RoboMaster 팀이 2021년에 공개한 "휠-레그 LQR" 유도 — 바퀴·다리(5절 링크를 가상 다리 하나로 환원)·몸체의 3체 평면 모델 — 을 MATLAB으로 그대로 재현해 LQR 게인을 다리 길이 L0에 대한 다항식으로 피팅하고, MCU에서는 `u = −K(L0)·x` 한 줄을 돌린다.

- 상태 6개: `x = [θ, θ̇, x, ẋ, φ, φ̇]` — θ 가상 다리의 기울기(고관절이 바퀴보다 앞이면 +), x 바퀴 위치, φ 몸체 피치(HEU 부호: 뒤로 젖히면 +).
- 입력 2개: `u = [T, Tp]` — T 바퀴 토크 합, Tp 고관절이 몸체에 주는 피치 토크(다리에는 반작용). 세 번째 자유도(다리 길이)는 **VMC로 분리**해 별도 PD로 지지력 F를 만들고, 5절 링크 야코비안으로 (F, Tp)를 두 관절 토크로 바꾼다.
- 따라서 "6-모터 균형 제어"의 균형 부분은 4-모터와 동일하게 상태 피드백이고, 추가된 것은 상태 2개(θ, θ̇)와 출력 1개(Tp)뿐이다. 다리 길이 제어는 균형과 결합되지 않는다(준정적 파라미터로 취급).

프로젝트별 차이는 (1) 다항식 차수와 상태 순서, (2) Q/R, (3) 다리별로 K를 적용하는지 전체로 적용하는지, (4) 펌웨어가 Tp 행을 실제로 쓰는지뿐이다. 소스를 끝까지 읽어 보니 **(4)에서 두 프로젝트가 "LQR"과 다르게 동작**했다(§8.3 B9, §8.3 B6).

### 8.2 테스트 환경 — 3체 휠-레그 플랜트 (`sim6/plant6.py`)

4-모터 비교(§2)의 2륜 역진자 플랜트는 다리 각도 상태가 없어 이 법칙들을 넣을 수 없다. 그래서 이 프로젝트들이 MATLAB에서 쓰는 **바로 그 3개 식**(sys_calc.m / chassis_calc_heu.m / model_LQR.m에 동일하게 들어 있는 HEU 식)으로 비선형 플랜트를 만들었다.

```
Nm = M (ẍ + (L+Lm)(θ̈ cosθ − θ̇² sinθ) − l (φ̈ cosφ − φ̇² sinφ)) − F        (F: 몸체 무게중심에 가하는 수평 외란)
Pm = M g + M ((L+Lm)(−θ̇² cosθ − θ̈ sinθ) − l (φ̇² cosφ + φ̈ sinφ))
N  = Nm + mp (ẍ + L (θ̈ cosθ − θ̇² sinθ)),   P = Pm + mp g + mp L (−θ̇² cosθ − θ̈ sinθ)
(1) ẍ = (T − N R)/(Iw/R + mw R)
(2) (P L + Pm Lm) sinθ − (N L + Nm Lm) cosθ − T + Tp − Ip θ̈ = 0
(3) Tp + Nm l cosφ + Pm l sinφ − Im φ̈ = 0
```

sympy로 가속도에 대해 선형인 꼴 `M_acc(q, q̇)·[ẍ, θ̈, φ̈] = rhs`로 정리해 매 스텝 수치로 풀고(RK4 1 ms), 선형화는 유한차분으로 한다. 다리 길이 L0는 매 스텝 바꿀 수 있는 파라미터이며 Ip(L0)는 USTB의 피팅식을 쓴다. 바퀴 점성 마찰 b·ẋ·R을 더했다.

**검증**: USTB Reborn(JerryGong0911)이 문서에 공개한 로봇 파라미터(R 0.076 m, m_w 0.47, m_p 1.874, M 6.975 kg, I_w 0.001974, I_M 0.143, l 0.0353 m, L = 0.1576 L0 + 0.0272, I_p = 0.0328 L0 + 0.0216)와 Q=diag(160,160,200,120,2000,50), R=diag(1,0.25)를 내 플랜트에 넣고 1 ms dLQR을 풀면, 그들이 펌웨어에 넣은 K(L) 2차 다항식(`k[12][3]`)과 다음과 같이 맞는다(바퀴 토크 행, L0 = 0.20 m):

| 항 | θ | θ̇ | x | ẋ | φ | φ̇ |
|---|---|---|---|---|---|---|
| 내 플랜트 dLQR | −48.2 | −11.4 | −10.0 | −14.5 | 26.4 | 5.2 |
| USTB 다항식 | −44.2 | −8.5 | −10.2 | −14.3 | 26.0 | 5.1 |

L0 = 0.15, 0.30 m에서도 5–10 % 안에 들어온다(`python3 plant6.py`). 즉 플랜트와 부호 규약이 이 프로젝트들의 설계 모델과 같고, 이 플랜트에서 균형이 안 되는 법칙은 이식 실수가 아니라 법칙 자체의 문제로 볼 수 있다. 개루프 고유값(RM급, L0 0.2 m)은 ±13.7, ±4.1 rad/s — **불안정 모드가 둘**(다리 모드 73 ms, 몸체 모드 245 ms)이라 4-모터 플랜트(6.9 rad/s 하나)보다 빠르다.

플랜트 5종으로 돌렸다: **RM급**(위 USTB 파라미터, 휠 6 Nm·고관절 30 Nm — 이 프로젝트들의 원래 로봇), **Liu Webots**(15 kg, 그 프로젝트의 문서 값), **Skythinker 탁상 로봇**(0.6 kg, sys_calc.m 값), 그리고 우리 목표인 **5 kg급·10 kg급 5절 링크 가정**.

하네스(`sim6/sil6_harness.py`)의 테스트 항목은 §2와 같고 다리 상태가 추가됐다: 다리 기울임/몸체 기울임 복귀 한계(2.5° 간격, 40°까지, 노이즈 포함), 100 ms 푸시 한계(**로봇 무게 W의 0.1–2.0배**로 정규화 — 0.6 kg 로봇에 10 N을 밀 수는 없으므로), 속도 스텝(0.8 m/s, 탁상 로봇 0.3 m/s), 지연 허용(0–80 ms), 다리 길이 1.4배 램프, 정지 토크 RMS, 고정 시나리오(다리 10°, 0.4 W 푸시). 센서 노이즈는 다리각 0.1°, 다리각속도 0.5°/s, 피치 0.2°, 자이로 0.5°/s, 엔코더 14비트.

**부호 탐색**: 프로젝트마다 IMU·모터·관절 영점의 극성이 다르므로 (θ, φ, T, Tp) 부호 16가지를 모두 시도해 2° 기울임을 복귀하고 가장 큰 푸시를 견디는 조합을 쓴다(Jerry는 플랜트와 같은 HEU 규약이라 전부 +). 그리고 **두 단계**로 평가했다. (a) **공개 게인 그대로**(출력 스케일 1) — 그 프로젝트의 제어기 자체. (b) **출력 스케일 탐색**(1/16–128배) — 다른 로봇용 게인을 이 로봇 무게에 맞게 키우거나 줄인 것. (b)는 "게인 비율은 그들 것, 크기만 조정"이다.

### 8.5 해석

1. **같은 법칙, 다른 로봇.** 9개 HEU 계열은 구조가 동일하므로 성능 차이는 전부 Q/R(게인 크기)에서 온다. 공개 게인은 자기 로봇 질량 근방에서만 그대로 쓸 수 있다: RM급(7 kg) 게인은 우리 10 kg급에 거의 그대로 통하고, 5 kg급에서는 USTB가 0.5배를 요구하며, 0.6 kg 탁상 로봇에는 어떤 것도 못 쓴다(반대로 Skythinker 게인은 RM급에 32배). "게인 복사"는 같은 급 로봇 사이에서만 의미가 있고, 그마저 아래 2번 때문에 위험하다.
2. **공개 게인은 빠르지만 지연에 약하다.** USTB·Zhouzzw·Liu·ATWheelLeg는 3–4 ms, QDU 8 ms에서 넘어진다. 토크 가중치 R이 싸서(USTB R=diag(1, 0.25) vs Q 최대 2000) θ̇·φ̇ 게인이 크기 때문이고, 같은 이유로 정지 상태에서 자이로 노이즈를 토크로 그대로 내보낸다(USTB 휠 0.34·고관절 0.48 Nm RMS, Liu 0.40/0.56, 5 kg급에서는 1.1/1.4 Nm; 내 LQI6 0.04–0.07 / 0.04–0.14 Nm). RoboMaster 로봇은 IMU와 CAN이 1 kHz로 같은 보드에 붙어 있고 1–2 ms 안에 닫히므로 그들에게는 문제가 아니지만, Teensy + CAN + 필터를 거치는 우리 구조(§2의 2–5 ms)에서는 USTB 게인은 여유가 0이다. 6-모터 플랜트는 불안정 모드가 둘(13.7, 4.1 rad/s)이라 4-모터보다 이 절충이 가파르다 — 내 첫 설계도 같은 함정에 빠졌었다(§8.3 표).
3. **푸시·틸트 한계는 변별력이 낮다.** 스케일을 맞춘 LQR 계열은 전부 40°/40°를 복귀하고 0.7–1.4 W 푸시를 견딘다(2배 안). 오히려 "가장 큰 푸시" 1위인 LJW(2.0 W)는 §5.3과 같은 함정 — 변위 0.2–0.3 m를 굴러가고 몸체가 13–22° 흔들리면서 버틴 것이다. 고관절이 위치 루프라 다리가 몸체에 붙어 하나의 진자가 되므로 몸체 피치를 따로 세울 수 없다. 반면 USTB·QDU·HNUST·내 LQI6는 변위 0.00–0.02 m, 몸체 0.3–1.4°로 제자리에서 버틴다.
4. **각 프로젝트의 특징.** HNUST는 10° 복귀 0.3 s로 가장 빠르지만 속도 스텝 오버슈트 90–100 %, 고관절 정지 토크 0.5 Nm(φ 게인 113). QDU는 가장 큰 푸시(1.3–1.4 W)지만 지연 0–10 ms·정지 토크 0.2 Nm. Multivac은 공개 게인 중 가장 보수적인 R(280, 17) 덕에 그대로도 15 ms·0.9–1.1 W이고 0.5배로 줄이면 30 ms·0.05/0.11 Nm로 내 LQI6와 같은 급이 된다. Zhouzzw는 Q가 USTB의 10–35배라 내 플랜트 토크 한계에서 뱅뱅이 되며(관절 80 Nm 한계로 보아 훨씬 강한 액추에이터용), 0.25–0.5배에서만 균형·지연 3 ms. Liu는 l = 0(몸체 무게중심을 고관절에 둠) 모델이라 l > 0인 로봇에서 몸체 기울임 한계가 10°(RM)·2.5°(5 kg)로 떨어진다 — 모델 가정이 이식성을 깬 예. ATWheelLeg는 게인이 USTB의 1/5로 무른 쪽이어서 다리 7.5–15°에서 한계가 오고 0.2 m를 굴러간다.
5. **내 LQI6.** 그들의 로봇(RM급)에서 푸시 1.2 W(QDU 1.4 다음), **지연 26 ms(1위)**, 정지 토크 최저, 속도 스텝 오버슈트 23 %·몸체 0.3°(최저), 변위 0, 다리 1.4배 변화 0.03°. 5 kg급·10 kg급·Liu·Sky 플랜트 전부에서 스케일·부호 조정 없이 같은 그림이다. 이유는 두 가지다 — 플랜트에서 리카티를 직접 풀어 게인을 만들고(다항식 피팅·다른 로봇 게인 복사 없음), R을 모터 토크 한계에 비례시켜 어느 크기의 로봇에서도 같은 절충이 유지되게 했다(절대값 R로 두었을 때는 0.6 kg 로봇에서 뱅뱅이 났다 — §8.3).
6. **6-모터와 4-모터의 관계.** θ 상태와 Tp 출력을 지우면 이 법칙은 §3의 4-모터 LQI와 같은 식이 된다. LJW가 실제로 그렇게 운전한다(고관절 위치 고정 + 바퀴 LQR 1행 × 0.4) — 균형은 잡히지만 몸체 흔들림이 10배 커진다. 5절 링크를 달아도 처음 세우는 단계에서는 이 방식이 가장 단순하고, 그다음 Tp 행을 켜는 순서가 합리적이다.

### 8.6 결론

- **6-모터 프로젝트에서 "제어기"를 가져올 이유는 없다.** 전부 HEU 3체 모델의 LQR이고, 내 LQI6가 같은 모델에서 더 넓은 지연 여유와 더 낮은 노이즈 토크로 같은 외란 한계를 낸다. 공개 게인은 로봇 질량에 묶여 있고 지연 여유가 3–8 ms라 Teensy+CAN 구조에서 그대로 쓸 수 없다.
- **가져올 것**: USTB의 **모델·파라미터 문서화와 VMC 코드**(5절 링크 야코비안으로 (F, Tp)→관절 토크, 다리 길이 PD) — 플랜트 검증에 쓴 바로 그 식이다; Skythinker의 **다항식 게인 스케줄링**(리카티를 MCU에서 못 풀 때의 대안); ATWheelLeg의 **공중 게인**(바퀴 이탈 시 다리만 세움); LJW의 **점프·착지 상태기계와 지면 접촉 검출**; HNUST·QDU의 **요·롤을 포함한 10상태 통합**(좌우 다리 길이가 다를 때); Multivac의 **보수적 R** 선택.
- **가져오지 말 것**: 게인 값 자체, Zhouzzw의 Q(토크 한계에서 뱅뱅), Liu의 l = 0 모델.
- **우리 로봇(4-모터)에 대한 결론은 §5.4 그대로다**: 내 LQI(1 kHz, 온라인 리카티, **R은 토크 한계 비례**)를 쓴다. 뒤에 5절 링크로 바꾸면 `sim6/controllers6.py`의 `MineLQI6`(다리 길이 스케줄링 포함)가 USTB 모델에서 검증된 상태로 준비돼 있다.

### 8.7 이 절의 한계

- Tp를 가상 고관절에 직접 가했다 — 5절 링크 야코비안·관절별 토크 한계·VMC 지지력 루프는 시뮬레이션에 없고 다리 길이는 준정적 파라미터다. 평면 모델이라 롤·요·좌우 다리 비대칭이 없고 HNUST·QDU의 10상태는 좌우를 합쳐 줄였다.
- RM급 플랜트의 토크 한계(휠 6·고관절 30 Nm)와 마찰, 5 kg·10 kg 5절 링크의 다리 질량·관성, Skythinker의 모터 한계, LJW의 CyberGear 위치 루프 강성(kp 5, kd 0.5)은 가정값이다.
- 부호 탐색은 16가지 중 가장 잘 되는 조합을 고른다. 잘못 이식된 법칙이 우연히 맞는 조합으로 통과할 수 있으므로, HEU 부호 패턴(T행 −−−−++, Tp행 ++++++)과 대조해 전부 설명되는지 확인했다(QDU 피치, Multivac 각도, AT·LJW 모터 극성만 반대). 스케일 탐색은 1/16–128배로 제한했다.
- B1(USTB)·B5(Multivac)의 저장소는 2026-10-20 현재 접근할 수 없다(§1.2). 결과는 조사 당시 받아 둔 소스 기준이며 재현하려면 그 사본이 필요하다.
- chen-jiangnan은 처음 받은 파일에 게인이 없어 빠졌고(전체 저장소에는 있음, §8 서두), 1772631792/WheelLeg_LQR은 4상태라 §5 하네스에서 평가했다(B10: 5 kg급 32.5°·30 N·지연 40 ms, 10 kg급 22.5–30°·60–70 N·40–60 ms — 다리각 피드백이 없어 푸시 한계가 LQR 4개 중 가장 낮다).
