# 시뮬레이션 환경 조사 — 조사 저장소 중 물리 시뮬레이터가 있는 4절·5절 링크 프로젝트

조사 저장소(제어기_비교보고서 §1·§8) 가운데 **물리 시뮬레이터**(MuJoCo, PyBullet, Webots, Simscape)를 포함한 것을 전부 추리고, 각각을 실제로 클론해 의존성·빠진 파일·OS 가정을 확인했다. 가능한 것은 이 컨테이너(Ubuntu 24.04.5, Python 3.13.16, 4코어, GPU·디스플레이·ROS 2 없음)에서 직접 돌려 봤다. 결과 파일·패치는 아래 각 절에 있다.

## 1. 4절 링크(Ascento형)

### S1. fernandomierhicks/wheeled-leg-robot — MuJoCo, 그대로 실행됨

- 위치: `simulation/mujoco/master_sim/` (물리 `physics.py`, 루프 `sim_loop.py`, 시나리오 `scenarios/s01…s09`, 최적화기 `optimizer/`, GUI `launcher.py`), `simulation/sil/`(실제 Teensy `control_loop.cpp`를 컴파일해 Python 포트와 골든 벡터 비교), `simulation/2d/`(4절 링크 치수 최적화 GUI).
- 모델: MJCF를 `physics.py`가 문자열로 생성(`from_xml_string`, 외부 메시 없음). 4절 다리를 `equality` 구속으로 닫고, `models/motor.py`·`latency.py`·`thermal.py`·`battery.py`로 모터 토크 한계·통신 지연·열·전압 강하를 넣는다. 다리 치수 프리셋 `2N_10mm_279mm`.
- 시나리오: s01 LQR 피치 스텝, s02 다리 높이 게인 스케줄링, s03 속도 PI 외란, s04 계단, s05 다리 주기 변화, s06 요 회전, … s09 통합. `evaluate()`가 헤드리스로 돌려 fitness를 돌려준다.
- 요구: `requirements.txt` — mujoco==3.6.0, numpy 2.5.2, scipy 1.18.0, matplotlib, pandas, pyqtgraph, PyQt6, pytest. 주석에 "Windows/Python 3.13"이라 쓰여 있지만 코드에 Windows 전용 경로·API는 없다.
- **직접 실행(Ubuntu 24.04, mujoco 3.16.0)**: `evaluate(DEFAULT_PARAMS, 's01_lqr_pitch_step')` → status PASS, survived 5.0 s, RMS pitch 3.49°, fitness 3.36, 벽시계 4.0 s.
- 빠진 것: 없음. GUI(`launcher.py`)는 tkinter+PyQt6+디스플레이가 필요하고, 헤드리스에서는 `evaluate()`만 쓰면 된다. 클론이 4.3 GB(미디어·CAD)이므로 `git clone --filter=blob:none --sparse` 후 `simulation firmware`만 체크아웃하는 편이 낫다. LICENSE 파일이 없다(저작권 유보 상태, 참고·개인 실험은 가능하나 재배포는 저자 확인 필요).

### S2. upkie/upkie — PyBullet(Gymnasium), pixi 권장

- `pip install upkie`(13.1.0, Python ≥3.10)로 Python 환경이 들어오고, `gym.make("Upkie-PyBullet-Pendulum")` 등이 `upkie/envs/backends/pybullet_backend.py`에서 pybullet을 지연 임포트한다. Bazel로 빌드하는 C++ 스파인은 "Spine" 환경에만 필요하다.
- **직접 실행**: `pip install pybullet`이 PyPI에 바이너리 휠이 없어 소스 빌드(Bullet 전체 C++ 컴파일)에 들어갔고 25분 제한에서 끊겼다. 저자도 `pixi run example-follow-joystick`(conda-forge 바이너리 pybullet) 경로를 권한다. 우분투에서 pixi를 깔면 바로 된다.
- 구조가 직렬 2관절 다리(고관절+무릎)라 4절·5절 어느 쪽과도 다르고, 제어기 비교(§6)에서 본 대로 속도 모드 의존이다. 시뮬 환경 자체(관측기, 환경 래퍼, 실로봇과 같은 코드)는 참고 가치가 있다.

### S3·S4. WL1, Venus-1 — 물리 시뮬레이터 아님

- WL1 `simulation/`: `WL1_LQR.py`(python-control로 4상태 LQR 게인 계산), `Leg_kinematics.py`(4절 운동학 그림), `WL1_LQR.m`. 우분투에서 돌아가지만 동역학 시뮬레이션은 없다.
- Venus-1 `4.Pyslvs simulation`: Pyslvs-UI로 4절 링크 궤적을 합성한 파일. 기구 설계용이지 제어 검증용이 아니다.

## 2. 5절 링크(6모터)

### S5. 1772631792/WheelLeg_LQR — MuJoCo(Python) + C 제어기, 패치 2곳 후 실행됨

- 구성: Tkinter 상위 앱(`main.py`), C 제어기(`controller/lqr.c`, `lqr_design.c`(리카티), `chassis.c`(VMC·길이 PID)), 참조 펌웨어 `balance_chassis-main`, MuJoCo 모델을 코드로 생성(`simulation/mujoco_model.py`, 5절/직렬 토폴로지 선택), 검증 스크립트(`verify`, `verify_chassis`, `verify_mujoco`, `verify_production_export`).
- 요구: `requirements.txt` — numpy, scipy, matplotlib, pillow, **mujoco==3.3.7**. C 빌드는 gcc(Makefile이 `.dll`·`.exe` 이름을 쓰지만 리눅스 gcc로도 ELF가 그 이름으로 만들어지고 ctypes가 그대로 읽는다).
- Windows 전용 부분(우분투에서 고쳐야 함):
  1. `controller/firmware.dll` 빌드: `riccati6.c`·`firmware_bridge.c`가 `__declspec(dllexport)`를 쓰고 `-Werror=return-type`에 걸린다. 아래처럼 직접 컴파일하면 된다.
     ```bash
     gcc -std=c11 -O2 -fPIC -shared '-D__declspec(x)=' -Icontroller/firmware_compat \
         -Ibalance_chassis-main/application/chassis controller/firmware_bridge.c controller/riccati6.c -o controller/firmware.dll
     ```
  2. `simulation/firmware_native.py`의 `close()`가 `_ctypes.FreeLibrary`(Windows)를 호출한다. 한 줄 교체:
     ```python
     (_ctypes.FreeLibrary(self.dll._handle) if hasattr(_ctypes, 'FreeLibrary') else _ctypes.dlclose(self.dll._handle))
     ```
  3. 헤드리스에서는 `verify_mujoco`가 렌더러를 만들므로 `sudo apt install libosmesa6` 후 `MUJOCO_GL=osmesa`로 실행(디스플레이가 있으면 불필요).
- **직접 실행**: `make PYTHON=python3 all`(controller.dll OK) → `make design`(리카티 11748회, SciPy DARE 일치) → `python3 -m simulation.verify` 전부 PASS(C/Python 궤적 오차 3e-8) → `verify_mujoco`:
  - mujoco **3.16.0**: stand PASS, ramp PASS, **step 실패**(계단에서 넘어짐, 피치 1.57 rad).
  - mujoco **3.3.7(고정 버전)** + osmesa: stand 0.001°, ramp 1.30°, step 3.12° **전부 PASS**, 물리+C+렌더 실시간 배율 0.32(소프트웨어 렌더).
  - 즉 **MuJoCo 버전을 반드시 3.3.7로 고정**해야 저자의 결과가 재현된다(접촉·적분기 기본값 차이).
- 빠진 것: 없음(패치 외). LICENSE 파일 없음. 4상태 균형 법칙이라 다리각은 제어에 안 들어간다(§8 B10).

### S6. lyz1202dt/ATWheelLeg — MuJoCo + ROS 2(ros2_control), ROS 없는 Core는 검증됨

- 구성: `Core/`(C++17 + Eigen, ROS 의존 없음: LQR·VMC·상태 추정), `MCU/`(STM32 펌웨어, CMakePresets), `MujocoSim/scr/`(ROS 2 워크스페이스 3패키지: `car` MJCF+URDF 36 KB, `controller` ros2_control 플러그인 `lqr_controller/LQRController`·`MujocoSimController` + `config/sim_controller.yaml`(17점 K표, VMC kp/kd, 토픽), `mujoco_ros2_control`(dfki-ric 포크)).
- 요구: ROS 2(배포판 미명시; 상류 mujoco_ros2_control은 Humble·Jazzy 지원, 코드는 C++17이고 2026-09 커밋이므로 Ubuntu 24.04 + **Jazzy**로 보면 된다), colcon, Eigen3, GLFW(`libglfw3-dev`), ros2_control(`controller_manager`, `hardware_interface`, `realtime_tools`, `pluginlib`), `cv_bridge`·`vision_opencv`·`pcl_conversions`·`perception_pcl`(깊이 카메라 플러그인용), `xacro`, `urdf`. **MuJoCo 3.2.7은 CMake FetchContent가 빌드 중에 GitHub에서 내려받는다** → colcon 빌드 때 인터넷이 있어야 하고 첫 빌드가 길다(MuJoCo 소스 빌드).
- 빠진 것: `third_party/TinyMPC`, `third_party/autodiff`가 **빈 디렉터리**(`.gitmodules` 없는 깨진 서브모듈)다. Core의 CMake는 시스템 Eigen3이 없으면 여기로 폴백하므로 `sudo apt install libeigen3-dev`가 필수다.
- **직접 실행(ROS 없는 부분)**: `apt-get update && apt-get install libeigen3-dev` 후 `cmake -S Core -B Core/build -DCORE_BUILD_TESTS=ON && cmake --build Core/build && ctest` → **빌드 성공, 테스트 1/1 PASS**. ROS 2 워크스페이스는 이 컨테이너에 ROS 2가 없어 빌드하지 못했다(우분투 24.04 + Jazzy에서 `colcon build --symlink-install --base-paths scr` 후 `ros2 launch controller sim_controller.launch.py show_gui:=true`).
- 제어 루프는 controller_manager 500 Hz로 ROS 2 안에서 돈다(§8 해석: 지연 허용 4 ms라 PC ROS 2에서는 여유가 적다). LICENSE 파일 없음(`mujoco_ros2_control` 하위만 라이선스 있음).
