# v5 로봇 전용 모델과 IMU (2026-11-07)

v5 시뮬레이션과 제어기에서 upkie의 URDF와 IMU 값을 빼고, Fusion 모델에서 뽑은 값으로 바꾼 기록이다.
실제 코드와 측정값의 위치를 함께 적었다. 측정은 모두 시뮬레이션이고 실기로 확인한 값은 아니다.

**11-07 사용자: 링크 25 cm(허브 버전 10).** 모델과 게인은 25 cm로 옮겼고 내용은 10절에 있다. 1절 대조표는 25 cm 값이고, 3~7절의 측정값은 17.5 cm 때 값이다.

## 2. pi3hat의 축과 프레임

[pi3hat docs/reference.md](https://github.com/mjbots/pi3hat/blob/master/docs/reference.md)의 "Orientation":
- 원시 IMU 축: **+x CAN 커넥터·Pi HDMI 쪽, +y Pi USB 쪽, +z Pi에서 hat 쪽**
- 자세의 기준 프레임: x 앞, y 오른쪽, z 아래(FRD). 장착 각도를 안 넣으면 "Pi를 뒤집어야 roll·pitch가 0"이다.

v5에서 잰 방향(Fusion, `v5run.imu_pose()`, 커넥터 형상까지 확인):

| pi3hat 축 | CAD 축 | 로봇 기준 |
|---|---|---|
| +x (CAN·HDMI) | +x | 뒤(무릎 쪽) |
| +y (USB) | +y | 오른쪽 |
| +z (Pi → hat) | +z | 위 |

그래서 **`R_base_to_imu` = diag(−1, −1, 1)**이다(z축 180°). 예전 코드의 `diag(−1, 1, −1)`은 Pi를 뒤집어 단 upkie의 값이었다. 시뮬레이션이 같은 상수로 쓰고 읽어서 시험에서는 드러나지 않았지만,
실기에서는 수평으로 선 로봇이 롤 180°로 읽혀 바로 FAULT가 났을 값이다(`tests/test_robot_v5.py`).

hat이 위를 보는 v5는 수평일 때 보드 자세가 롤 180°로 나온다(`q ≈ (0, 1, 0, 0)`). 정상이고, `R_ars_to_world = diag(1, −1, −1)`이 이것을 수평으로 되돌린다. 보드의 요 0은 자기 +x(로봇 뒤)라서 베이스 요는 180°로 나오지만, 제어기는 롤·피치와 요 속도만 쓰므로 영향이 없다:

```
R_base_to_world = R_ars_to_world · R_imu_to_ars(보드 쿼터니언) · R_base_to_imu
```

실기 설정: `mounting_deg`는 0, 0, 0, `attitude_rate_hz`는 1000(라이브러리 기본값 400).

`images/13_imu_axes.png`에 표시했다.

## 3. IMU 위치

강체에서 **각도와 각속도는 어느 점에서나 같다.** 위치가 들어가는 것은 가속도계뿐이다: `a_imu = a_hip + α × r + ω × (ω × r)`.
DIABLO 논문에서 IMU를 hip 축 중앙에 둔 것은 몸통 프레임의 원점을 거기 잡기 위해서이고, 논문 식에도 우리 플랜트에도 IMU 위치 항은 없다.
논문이 IMU 때문에 언급한 오차는 위치가 아니라 **장착 각도**다(Fig. 9의 θ 치우침).

측정(시드 3개, 1 kHz, 지연 10 ms, 잡음 켬, 추정 오차는 50 ms 평균의 최대). 로봇 좌표로 이전 칩 위치 (−8, +68.3, −35.5) mm, 새 위치 (−0.5, −2.45, −35.5) mm, hip 중앙 (0, 0, 0):

| 보드 자세만 쓸 때 | 이전 위치 | 새 위치 | hip 중앙 |
|---|---|---|---|
| 제자리 2 rad/s: 피치 추정 오차 | 0.28° | 0.06° | 0.06° |
| 1 m/s + 2 rad/s: 피치 추정 오차 / 실제 롤 최대 | 1.56° / 1.06° | 1.78° / 1.22° | 1.78° / 1.22° |
| 밀기 0.5 W: 실제 피치 최대 | 3.44° | 3.52° | 3.54° |
| 1 m/s 출발·정지, 턱 | 차이 없음 | | |

- 새 위치와 hip 중앙은 같은 값을 낸다. 즉 높이(hip 축 아래 35.5 mm)는 영향이 없다.
- 옆(y) 오프셋의 영향은 **주행·회전 방향에 따라 부호가 바뀐다.** 스위치 쪽 앞 기준의 왼쪽 회전에서는 이전 위치가 오히려 작게 나오고(1.56°), 같은 회전을 무릎 쪽으로 주행하면 크다(앞을 무릎 쪽으로 두고 쟀을 때 2.10°, 새 위치 1.78°). 제자리 회전 오차는 위치와 함께 커진다.
- 그래서 전장 데크에서 **Pi와 pi3hat을 중심선으로 옮겼다**(`torso.centre_imu()`, `v5run.relayout()`). 방향에 따른 치우침이 없어지고, 제자리 회전 오차가 줄어든다. 높이를 hip 축까지 올리는 것은 41 mm 받침이 더 필요하고 재본 이득이 없어 하지 않았다.
- 몸통 무게중심의 옆 치우침도 CAD y −0.71 → −0.13 mm로 줄었다.

## 4. 시뮬레이션의 IMU 경로

```
MuJoCo 사이트 imu(칩 위치, 원시 축) → 자이로·가속도(지렛대 효과 포함) → 센서 잡음(자이로 0.5°/s, 가속도 0.05 m/s²)
→ pi3hat 펌웨어 필터 포팅(wbr/observers/pi3hat_ars.py, UKF 7상태, 같은 잡음 값) → 지연 10 ms → MCU
```

`wbr/plans/plan_v5.py`. 예전에는 참 자세에 흰 잡음 0.2°를 얹었다(`imu_model="ideal"`로 비교 가능). 합격기준의 흰 잡음은 Plan 4(upkie) 판정에 그대로 남겼다.

펌웨어 필터를 넣자 두 가지가 드러났다.

**가속도를 기울기로 읽는다.** 필터가 가속도계를 중력으로 본다. 수평인 몸통이 2 m/s²로 0.5 s 가속하면 1.6°(전원 켠 뒤 1분 기준) 틀어지고, hip이 그 값을 따라가 몸통이 실제로 기운다.

**회전 후 요 속도가 틀어진다.** 펌웨어에는 yaw 관측이 없어서 "요 속도 0" 가짜 측정이 z 바이어스를 끌어간다. `rate_dps`를 그대로 요 제어에 쓰면 회전이 끝나도 로봇이 계속 돈다.

## 5. MCU의 자세 추정

DIABLO 논문의 구조(III-C절 "IMU, 모터 엔코더, 모터 드라이버 정보를 쓰는 상보 필터 기반 상태 추정기")대로 MCU에 상보 필터를 넣었다. `wbr/observers/body_attitude.py`.

```
위 방향 ẑ: 자이로로 적분, 시간 상수 5 s로 (f − a_imu) 방향에 맞춤
a_imu = a_hip + α × r + ω × (ω × r)      r: hip 중앙에서 IMU까지 (여기에 IMU 위치가 들어간다)
a_hip = d/dt(v + d/dt(L0 sin θ), d/dt(L0 cos θ)), 옆으로 ω_z · v
```

충격 중에는(로봇 자체 가속도 3 m/s² 초과, 또는 보정 후 크기가 1 g에서 1 m/s² 넘게 벗어남) 가속도 보정을 건너뛰고 자이로만 쓴다.
요 속도는 원시 자이로(`rate − bias`)에서, 바퀴가 돌지 않을 때 배운 오프셋을 뺀 값이다(`McuParams.yaw_offset_tau` 20 s).

| 시드 3개, 새 위치 | 보드 자세·속도만 | **MCU 필터** | 참 자세(비교용) |
|---|---|---|---|
| 1 m/s 출발·정지: 피치 추정 오차 / 실제 피치 최대 | 1.49° / 3.92° | **0.14° / 2.56°** | — / 2.46° |
| 1 m/s + 2 rad/s: 피치 / 롤 추정 오차 | 1.78° / 1.02° | **0.13° / 0.15°** | — |
| 밀기 0.5 W: 실제 피치 최대 | 3.52° | **3.32°** | 3.37° |
| 턱 4 cm 0.5 m/s: 실제 피치 최대 | 2.76° | **1.84°** | 1.81° |
| 2 rad/s 6 s 뒤 / 30 s 뒤 남은 요 속도 | 0.157 / 0.69 rad/s | **0.000 / 0.000 rad/s** | 0.000 |

이 필터에서는 이전 위치도 hip 중앙과 같은 값을 낸다(위치를 알려 줄 때). 위치를 무시하면(r = 0) 이전 위치의 제자리 2 rad/s 피치 오차가 0.05 → 0.19°가 된다. 새 위치에서는 무시해도 차이가 없다.

실기 브리지에서 받을 값(pi3hat 라이브러리 `Attitude`, `request_attitude_detail`):
- 원시 자이로 = `rate_dps − bias_dps`, 원시 가속도 = `accel_mps2 + 9.81 × conj(q)·(0, 0, −1)`(펌웨어 `OrientationToAccel`: ARS 프레임의 위 방향을 IMU 축으로 본 값, hat이 위인 정지 상태에서 (0, 0, +1); 물리적인 아래 방향으로 넣으면 부호가 틀린다)
- 시뮬레이션의 `obs["imu"]`: `orientation`(보드 쿼터니언), `angular_velocity`(`rate`), `bias_rps`, `linear_acceleration`(원시)

지연 여유(밀기 0.25 / 0.5 / 1 W × 시드 2개, 마지막 3 s 피치 흔들림 3° 초과를 "떨림"으로 셈):

| 센서 → 토크 지연 | 10 ms | 11 ms | 12 ms | 13 ms |
|---|---|---|---|---|
| 전체 제어기, 펌웨어 필터 + MCU 필터 | 0/6 | 0/6 | 4/6 | 6/6 |
| 전체 제어기, 참 자세 + 흰 잡음 | | | 4/6 | 6/6 |
| 순수 LQR, 펌웨어 필터 + MCU 필터 | | 4/6 | 6/6 | 6/6 |
| 전체 제어기, 예전 upkie 모델 경로(`--model upkie`, 무릎 쪽이 앞) | | 0/6 | 2/6 | 6/6 |
| 순수 LQR, 예전 upkie 모델 경로 | | 0/6 | 6/6 | |

IMU 경로는 지연 여유를 줄이지 않는다(위 두 줄이 같다). 모델을 바꿔도 시작점이 12~13 ms로 거의 같다. 단계 시험은 10 ms에서 돌므로 이 절벽을 보지 못한다. 10 s 안에 넘어지지는 않았지만 12 ms부터 몸통 피치가 8~10° 폭으로 흔들리고 다리 토크 명령 `Tp`의 rms가 19~22 N·m까지 오른다.

**2-13의 hip 피크: 다리 벌어짐 PD의 D항.** 충격이 눌린 쪽 hip으로만 들어가 좌우 다리 각속도 차가 커진다. `tau_split` 최대 13.2(앞) / 7.5 N·m(뒤).

**2-5의 다리 길이 오차: 기울기에서의 정적 힘.** 무릎 결합 보상 문제가 아니다. 다리 무게중심이 무릎 쪽에 있어 정적 기울기가 +3.8°이고, 경사가 더해지면 스위치 쪽 오르막에서 8.9°, 내리막에서 −0.9°가 된다. 제어기는 `F_ff / cos θ`를 쓰는데, 필요한 힘은 `½ g [(m_b + m_l c') cos θ − m_l d' sin θ]`다(`d' = 0.49`: 다리 길이가 변할 때 다리 무게중심이 앞뒤로 움직인다).

## 7. 과속방지턱: 서스펜션과 감속 (11-07 사용자: 속도보다 안정성, 부드럽게, 다리가 턱에 순응)

**다리.** 이전에는 평균 다리 길이를 유지해서 한쪽 바퀴가 올라가면 몸통도 턱 높이의 절반만큼 들리고 반대쪽 다리가 늘어났다. 이제 긴 쪽 다리의 길이를 유지한다(`McuParams.suspension`). 턱에 오른 다리는 밀어내는 힘 없이 접히고 몸통 높이는 거의 그대로다. 다리별 댐퍼(`kd_leg_own`)가 바퀴 튐을 막는다. 다리 차가 50 mm를 넘으면 반대쪽 다리도 서서히 함께 움직여(`suspension_share`) 어느 쪽도 범위 끝에 갑자기 닿지 않는다. 벽은 기존의 절반으로 무르게 했다(`LEG_WALL_SCALE`).

**20 cm가 완전히 수평이 되지 않는 이유.** 수평이려면 다리 길이 차가 200 mm여야 하는데 쓸 수 있는 범위가 약 144 mm(200~344 mm)다. 남는 56 mm가 윤거 540 mm에 대해 약 6°다.
- 무릎을 더 펴도 효과가 작다. 거의 펴진 다리는 무릎 각도가 크게 변해도 길이가 조금만 변한다(339 mm 29°, 345 mm 19°, 349 mm 9°, 350 mm 0°). 349 mm까지 펴도 롤은 6.6°에서 5.8°다. 벽을 344 mm 이상으로 두면 무릎이 반대로 꺾였다.
- 더 짧게 접는 쪽(200 mm 아래)은 Fusion 간섭 검사 범위 밖이라 쓰지 않았다.

**반대쪽 다리의 움직임.** 긴 쪽 다리는 기준을 2~25 ms 지연으로 따라간다. 늦어 보이는 것은 제어 지연이 아니라 필요할 때까지 움직이지 않게 설계했기 때문이다. 눌린 다리가 80 mm 접혔을 때 8 mm, 110 mm일 때 19 mm, 130 mm일 때 26 mm 움직인다.

**속도.** 다리 길이 차가 5 mm를 넘는 순간부터 제한이 내려와 30 mm에서 0.2 m/s가 된다(`uneven_speed`, `uneven_d0`, `uneven_d1`). 기준은 0.8 m/s²로, 0.2 s 필터를 거쳐 내려가고(`uneven_brake`, `uneven_brake_tau`), 다리를 그만큼 뒤로 기울인다(`uneven_lean`: 균형 로봇은 기울어야 감속한다). 다리 차가 없어지고 0.5 s 뒤 1 m/s²로 돌아온다. 주행 중 다리 차가 있는 동안 위치·기울기 적분을 멈춘다(`uneven_hold_int`): 멈추지 않으면 늦어진 만큼 따라잡으려고 0.5 m/s로 다시 가속했다.
