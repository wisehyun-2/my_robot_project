# 13. v5 로봇으로 옮길 때

> 이 장은 코드를 만들지 않는다. 01~12장에서 배운 것을 v5 로봇의 ROS 2 패키지(아직 없다)로 옮길 때 **무엇이 그대로이고 무엇이 달라지는지**, 이 가이드가 **어디까지 준비시키는지**를 적는다.
> v5에 대한 사실은 저장소 문서에 적힌 것만 쓴다. `wheeled_biped/ros2_ws/README.md`는 "ros2_ws README N절", 루트 `README.md`는 "루트 README", `references/README.md`는 "references README"라고 부른다. 문서에 없는 내용은 "저장소 문서에는 없지만 일반 지식에 따르면 ~"로 구분한다.
> **이 장은 결정을 대신하지 않는다.** 이미 정해진 것은 "정해졌다(README N절)", 제안만 있는 것은 "제안", 아직 비어 있는 것은 "정할 것"이라고 적는다. v5 문서의 내용은 길게 옮기지 않고 가리키기만 한다. ros2_ws README는 2026-11-15 기준이고 `src/`에 패키지가 아직 없다.

## 1. 대응표: bumperbot에서 배운 것 → v5 패키지 구조 안

v5의 패키지 구조 안은 ros2_ws README 3절에 있다(`[추가]`, `[수정]`은 제안이고 확정이 아니다). 패키지 구조는 TITA의 `ros2_control` 구조를 따르기로 정해졌다(ros2_ws README 2절, 11-08 사용자).

## 2. 달라지는 점

항목마다 "bumperbot에서는 / v5에서는 / 새로 배울 것 / 참고할 곳" 순서로 적는다.

### 2.1 명령 인터페이스: velocity 2개 → effort 6개

- **bumperbot에서는.** 바퀴 조인트 둘에 `velocity` 명령(03장). 속도를 목표에 맞추는 PID는 아두이노 안에서 돈다(11장). ros2_control은 속도 목표만 보낸다.
- **v5에서는.** 제어기 출력은 토크(effort)뿐이고 실물과 모든 시뮬레이터에서 같다(정해졌다, ros2_ws README 2절). 관절마다 `effort` 명령이다. 값은 N·m이고 moteus의 피드포워드 토크로 만든다(ros2_ws README 4.3절). 관절은 6개다(루트 README: AKE60-8 × 6).
- **`<ros2_control>` 태그의 모양만 본다.** 아래 첫 블록은 이 가이드의 `bumperbot_ros2_control.xacro`에서 한 조인트 부분이다(03장). 둘째 블록은 그것을 v5 모양으로 바꿨을 때의 **형태**일 뿐이고 v5 파일이 아니다. 괄호 안은 자리표시자다. 조인트 이름, 플러그인 이름, 센서 이름은 README에 아직 없다.

```xml
        <joint name="wheel_left_joint">
            <command_interface name="velocity">
              <param name="min">-1</param>
              <param name="max">1</param>
            </command_interface>
            <state_interface name="position" />
            <state_interface name="velocity" />
        </joint>
```

```xml
<ros2_control name="(이름)" type="system">
  <hardware>
    <plugin>(플러그인 이름)</plugin>
    <param name="(설정 이름)">(값)</param>
  </hardware>

  <joint name="(조인트 이름)">            <!-- 이 블록이 6개 -->
    <command_interface name="effort"/>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
    <state_interface name="effort"/>
  </joint>
</ros2_control>
```

- **새로 배울 것.**
  - `effort`는 `hardware_interface_type_values.hpp`의 표준 이름 `HW_IF_EFFORT`다. 이 가이드는 `velocity`만 다뤘다.
  - `min`/`max`는 기본 설정에서 강제되지 않는다(03장 단계 2의 설명에 확인 결과가 적혀 있다). 토크 상한은 다른 곳에서 정해야 한다. README는 moteus 명령의 `maximum_torque`를 말한다(4.1절 1번). CM 쪽의 `enforce_command_limits`(yaml에 `true`를 넣으면 잘린다)는 03장에서 확인했다.
  - 표준 제어기 `effort_controllers/JointGroupEffortController`가 설치돼 있다(`share/effort_controllers/`의 플러그인 xml로 확인했다). 03장의 `velocity_controllers/JointGroupVelocityController`와 같은 계열이다. README 6절 A3의 "관절마다 + 토크로 부호 시험"에 쓸 수 있을지는 이 가이드에서 돌려 보지 않았다(일반 지식에 따르면 같은 방식으로 숫자 배열을 토픽으로 보낸다).
- **참고할 곳.** `ros2_control_demos`에서 `effort` 명령 인터페이스를 쓰는 예제는 찾지 못했다(`name="effort"` 검색 결과 없음). 위치·속도·가속도는 예제 3이 보여 준다.

### 2.2 상태 인터페이스: IMU와 드라이버 상태를 제어기까지

- **bumperbot에서는.** 제어기가 읽는 상태는 바퀴의 `position`, `velocity` 둘이다. IMU는 **ros2_control 밖**에 있다. 시뮬레이션에서는 Gazebo 센서가 `ros_gz_bridge`를 거쳐 `/imu/out` 토픽으로 나오고, 실물에서는 참조의 Python 노드 `mpu6050_driver.py`가 토픽으로 낸다. 시뮬레이션 쪽은 참조 Section11이고 이 가이드의 09장이 다룬다. 실물 쪽은 참조 Section12에만 있고 이 가이드는 싣지 않으며 12장이 한 줄로 언급한다. 09장의 시험에서 IMU로 융합한 EKF는 방향이 실제와 같아졌고(네 번 돌려 오차 0.0002 rad 이하, 실행마다 조금 다를 수 있다) 위치는 노이즈 오도메트리보다 나아지지 않았다. 이 값들은 ros2_control을 거치지 않고 토픽으로 들어온 것이다.
- **v5에서는.** 상태를 제어기까지 올린다(ros2_ws README 4.1절 7번, 4.3절). 요약만 적는다. 값의 뜻과 단위는 4.3절이 기준이다.
  - 관절: `position`, `velocity`, `effort`, 그리고 `mode`, `fault`, `home_state`, 전압, 온도(드라이버 상태. 시뮬레이션에는 없다).
  - IMU: `orientation`, `angular_velocity`, `linear_acceleration`, 자이로 바이어스, 표본 시각.
  - 요청한 상태 인터페이스가 하나라도 없으면 제어기 활성화가 실패한다. 그래서 요청 목록을 파라미터로 바꾼다(실물: 바이어스·표본 시각·`home_state` 포함, 시뮬레이션: 표준 값만)(4.3절).
- **bumperbot과 달라지는 구조.** bumperbot의 `bumperbot_ros2_control.xacro`는 `is_sim`으로 `<hardware>`만 가르고 조인트와 인터페이스 목록은 공통이다(03장 단계 8의 "1번은 그대로"). v5는 같은 방식으로 되지 않는다. 시뮬레이션에는 없는 인터페이스가 실물에는 있으므로 **인터페이스 목록도 `hw_env`에 따라 달라진다**(README 4.3절의 "시뮬에는 없음"). 그 방법(xacro에서 갈라 쓸지 등)은 정할 것이다.
- **새로 배울 것과 참고할 곳.** 설치된 헤더와 예제에서 확인한 것만 적는다.
  - `hardware_info.hpp`의 `HardwareInfo`는 `joints`, `sensors`, `gpios`를 따로 가지고 각각 `state_interfaces`를 가진다. `sensors`는 "Required for Sensor and optional for System"이므로 `system` 컴포넌트 안에 `<sensor>`를 둘 수 있다. `InterfaceInfo`의 `data_type`은 기본이 `double`이고, 파서(`HandleDataType`)가 받는 이름은 `double`, `bool`, `float32`, `uint8`, `int8`, `uint16`, `int16`, `uint32`, `int32`뿐이다. `int`는 받지 않는다(주석의 "e.g. bool, int"는 느슨한 예시다). `mode`, `fault` 같은 정수 값을 올린다면 `int32` 같은 이름을 써야 한다.
  - IMU의 표준 이름은 `<센서 이름>/orientation.x`, `angular_velocity.x`, `linear_acceleration.x` 같은 형태다(`#include`에 쓰는 이름은 `semantic_components/imu_sensor.hpp`, 파일은 `/opt/ros/jazzy/include/controller_interface/semantic_components/`에 있다). README 4.3절의 세 값과 이름이 같다. 바이어스와 표본 시각은 표준 이름에 없다(이 헤더에서 찾지 못했다).
  - 표준 이름 상수에 `temperature`는 있다(`hardware_interface_type_values.hpp`). `mode`, `fault`, `home_state`는 없다. 조인트에 임의 이름의 state interface를 둘 수 있는지는 확인하지 못했다. 임의 이름은 `<gpio>`에서 쓰는 예가 있다.
  - 설치된 브로드캐스터: `imu_sensor_broadcaster`(IMU를 토픽으로), `state_interfaces_broadcaster`(요청한 state interface를 토픽으로 낸다는 설명). 이들은 이 가이드에서 돌려 보지 않았다. `gpio_controllers`는 브로드캐스터가 아니라 GPIO에 명령을 쓰는 제어기(`gpio_controllers/GpioCommandController`)다.
  - 예제: `ros2_control_demos`의 예제 4(`system` 안의 `<sensor>`), 예제 5(독립 `type="sensor"` 컴포넌트), 예제 10(`<gpio>`에 임의 이름의 state·command interface), 예제 14(액추에이터와 센서를 컴포넌트로 따로), 예제 17(하드웨어 컴포넌트가 CM이 넘겨 준 executor로 진단을 토픽으로 낸다). 어느 예제가 무엇을 보여 주는지는 `references/ros2_control_demos/README.md`와 각 `example_N/doc/userdoc.rst`에서 확인했다.
- **정할 것.** 드라이버 상태를 조인트의 추가 state interface로 둘지 `<gpio>`나 `<sensor>`로 둘지, IMU를 같은 `system` 안에 둘지 따로 둘지, 인터페이스 이름. README는 값의 뜻을 정했고 이름은 정하지 않았다.

### 2.3 제어기 플러그인을 직접 쓴다 (이 가이드의 가장 큰 빈칸)

- **bumperbot에서는.** 표준 제어기(`diff_drive_controller`, `joint_state_broadcaster`, `JointGroupVelocityController`)와 일반 노드 `simple_controller`만 다룬다. 05장 단계 4의 비교표는 "알고리즘을 바꾸려면 제어기 플러그인을 직접 써야 한다"고 적고 거기서 멈춘다. 
- **v5에서는.** 균형 제어기(LQI8, 나중에 MPC)가 CM의 제어 루프 안에서 돌아야 한다. 근거는 다음과 같다.
  - 제어 주기 목표가 1 kHz다(ros2_ws README 2절). 05장 단계 4가 밝힌 대로 토픽을 거치는 구성 A는 토픽 지연이 있고, 매 주기 상태를 읽고 토크를 쓰는 균형 제어는 CM 안의 제어기(구성 B)가 맞다.
  - README는 래퍼의 틀을 `ros2_control_demos`, `rl_controller`, `template_ros2_controller`에서 참고하라고 하고(6절 A5), 끌 때 `on_deactivate`에서 토크 0을 쓴다고 적는다(4.4절 5번). `ros2_control_demos`에는 제어기 예제(예제 7, 12)가 있고, `rl_controller`는 `ControllerInterface`를 상속한 제어기 플러그인이다(헤더를 열어 확인했다). `template_ros2_controller`는 열어 보지 못했다(아래).
  - 그러나 문서에 "`wbr_controller`는 제어기 플러그인이다"라고 못 박은 문장은 확인하지 못했다. 위 근거에서 그렇게 읽을 뿐이다.
- **이 가이드에는 제어기 플러그인을 쓰는 법이 없다.** 11장은 하드웨어 컴포넌트만 다룬다. 두 플러그인은 구조가 닮아서 11장의 지식이 상당 부분 재사용된다.

| 항목 | 하드웨어 컴포넌트(11장) | 제어기 | 근거 |
|---|---|---|---|
| 기반 클래스 | `hardware_interface::SystemInterface` | `controller_interface::ControllerInterface`. 체인형이면 `ChainableControllerInterface`(`update()` 대신 `update_reference_from_subscribers()`와 `update_and_write_commands()`를 구현한다) | 설치된 헤더 |
| 초기화 | `on_init(params)`. URDF 정보(`info_`)를 받는다 | `on_init()`. 파라미터를 선언한다 | `controller_interface_base.hpp`의 `on_init() = 0` |
| 생명주기 콜백 | `on_configure`, `on_activate`, `on_deactivate`, `on_cleanup` | 같은 콜백 | 10장 단계 2의 대응표 |
| 주기 함수 | `read()`, `write()` | `update(time, period)`(`= 0`). 헤더 주석은 실시간 안전해야 한다고 적는다 | `controller_interface_base.hpp` |
| 인터페이스 | URDF에서 핸들이 **자동으로** 만들어지고 이름으로 접근한다 | `command_interface_configuration()`, `state_interface_configuration()`으로 쓸 **이름을 요청한다**. 없는 이름이면 활성화가 실패한다 | 헤더, `example_7` 문서 |
| 설정을 받는 곳 | URDF의 `<param>` | yaml(ROS 파라미터) | 03장, `example_7` |
| 등록 | `pluginlib_export_plugin_description_file(hardware_interface <xml>)`, xml의 `base_class_type`은 `hardware_interface::SystemInterface` | `pluginlib_export_plugin_description_file(controller_interface <xml>)`. `base_class_type`은 체인형이 아니면 `controller_interface::ControllerInterface`, 체인형이면 `controller_interface::ChainableControllerInterface` | CMake: `example_7`·`example_12`. xml: `example_7`의 `ros2_control_demo_example_7.xml`(`ControllerInterface`), `example_12`의 `passthrough_controller.xml`과 설치된 `diff_drive_plugin.xml`(`ChainableControllerInterface`), 설치된 `effort_controllers`의 xml(`ControllerInterface`) |
| 이름으로 연결 | URDF `<plugin>` = xml `class name` | yaml `type:` = xml `class name` | 03장, 11장 |
| 올리는 쪽 | resource manager(URDF를 받을 때) | 스포너가 CM 서비스로 load → configure → activate | 03장 |

`example_7`의 설명 xml(`ros2_control_demo_example_7.xml`)은 한 파일에 하드웨어 클래스(`RobotSystem`)와 제어기 클래스(`RobotController`)를 함께 적는다. 같은 라이브러리에 두 플러그인이 들어갈 수 있다는 뜻이다. README 3절의 안은 `wbr_hardware`와 `wbr_controller`를 별도 패키지로 둔다. 이 장은 그것을 바꾸자는 것이 아니다.

- **새로 배울 것.**
  - `command_interface_configuration()`이 돌려주는 `InterfaceConfiguration`(`ALL`, `INDIVIDUAL`, `NONE`, `INDIVIDUAL_BEST_EFFORT`, `REGEX`)으로 6개 관절의 effort와 IMU 이름을 정확히 요청하는 방법.
  - 토픽으로 받은 명령(`cmd_twist` 등)을 `update()`의 실시간 스레드로 넘기는 방법. `example_7`은 `realtime_tools::RealtimeThreadSafeBox`를 쓴다(`r6bot_controller.hpp`).
  - `update()` 안에서 하면 안 되는 것. 헤더는 `update()`가 "real-time safe and thread-safe"여야 한다고 적고, `get_lifecycle_state()`를 제어 루프에서 부르지 말고 캐시된 `get_lifecycle_id()`를 쓰라고 적는다.
  - ROS가 없는 `core`를 `update()`에서 부르는 얇은 래퍼로 두는 구조(ros2_ws README 3절, 6절 A4~A5). 이 가이드에는 이런 분리의 예가 없다. `core`만 링크해 Python 기준 기록과 비교하는 시험이 README 6절 A4의 `test_equivalence`다.
  - 제어기 파라미터를 선언하는 `generate_parameter_library`. README 1절 (b)의 apt 목록에 있고 `example_12`가 쓴다(`passthrough_controller_parameters.yaml`). 이 가이드는 쓰지 않았다.
- **참고할 곳.**

  2. **`references/ros2_control_demos/example_7`** 이 가장 가깝다. `doc/userdoc.rst`의 "Writing a controller"가 `ControllerInterface`를 상속해 `command_interface_configuration`, `state_interface_configuration`, `update`, `on_init`, `on_configure`, `on_activate`, `on_deactivate`를 쓰는 순서를 설명하고, `controller/r6bot_controller.cpp`가 그 구현이다. 주의: 이 문서는 `ros2_control_node`를 돌리려면 `robot_description` **파라미터**가 있어야 한다고 적는데, 이 가이드가 쓴 4.50에서 CM은 `/robot_description` **토픽**으로 받고 파라미터는 무시한다(12장 단계 3).

### 2.4 시뮬레이터: Gazebo → MuJoCo 먼저

- **bumperbot에서는.** Gazebo의 `gz_ros2_control`. URDF에 `<gazebo><plugin filename="gz_ros2_control-system">`을 붙이고(03장 단계 4) `<hardware><plugin>`에 `gz_ros2_control/GazeboSimSystem`을 쓴다. CM은 Gazebo 프로세스 안에서 뜬다. `GazeboSimSystem`은 `gz_ros2_control`이 자기 목록(`gz_ros2_control__pluginlib__plugin`)에서 찾는 클래스다(00장 3.3).
- **v5에서는.** 시뮬레이터는 공식 `mujoco_ros2_control`을 **먼저**, 그 뒤 Gazebo와 Isaac Sim이다(정해졌다, ros2_ws README 2절). 제어기 출력은 어느 시뮬레이터에서든 같은 토크다. ROS 시뮬은 연결 확인용이고 합격 판정은 Python 단계 시험과 C++ 일치 시험으로 한다(5.4절).
- **구조.** 03장 단계 8의 결론이 그대로 쓰인다. 바뀌는 것은 `<hardware><plugin>`과 시뮬레이터를 띄우는 launch이고, 제어기와 yaml은 그대로다(2.2의 인터페이스 목록 차이는 예외다).
- **이 노트북에 `mujoco_ros2_control`은 설치돼 있지 않다.** `ros2 pkg prefix mujoco_ros2_control`이 `Package not found`를 냈다(2026-11-21). 설치는 ros2_ws README 1절 (b)의 `sudo apt install ... ros-jazzy-mujoco-ros2-control ...`다. (`mujoco_vendor`는 `/opt/ros/jazzy`에 있지만 이름이 다른 패키지다.)
- **새로 배울 것.** 이 가이드에서 확인하지 못한 것이다.
  - MuJoCo 쪽에서도 시뮬레이터 안의 플러그인이 CM을 띄우는지, `<plugin>` 이름을 누가 푸는지.
  - MJCF와 URDF가 어떻게 이어지는지, IMU와 센서를 어떻게 내놓는지.
  - 물리 스텝과 CM 주기가 맞물리는 방식. ros2_ws README 7절이 "확인하지 못한 것"으로 적었다(물리 0.5 ms와 제어 1 kHz). bumperbot에서 같은 종류를 먼저 본다. Gazebo 물리 스텝 0.001 s보다 CM 주기 0.01 s가 길다는 경고가 03장 단계 5에 있다.
  - 확인 방법: 설치한 뒤 README 1절 (b)의 `ros2 launch mujoco_ros2_control_demos 01_basic_robot.launch.py`와 패키지의 `share/`(플러그인 xml)를 연다.
- **참고할 곳.** `ros2_control_demos` 예제 9. 한 xacro에서 `use_gazebo` 인자로 `gz_ros2_control/GazeboSimSystem`과 자기 하드웨어 플러그인을 갈라 쓰고, launch가 둘로 나뉜다(`rrbot.launch.py`, `rrbot_gazebo.launch.py`). bumperbot의 `is_sim`과 같은 모양이다.

### 2.5 하드웨어 플러그인: 시리얼 + 아두이노 → pi3hat + moteus

- **bumperbot에서는(11장, 12장).** `on_init`에서 URDF의 `port` 파라미터를 읽고 조인트 이름을 검사한다(URDF 쪽은 12장의 `<param name="port">$(arg port)</param>`). `on_configure`에서 시리얼 포트를 열고, `on_deactivate`에서 정지 명령을 보내고, `on_cleanup`에서 닫는다. `read()`는 도착한 바이트만 읽고(블로킹 금지), `write()`는 명령 문자열을 보낸다. 주기 100 Hz. 12장에서 가짜 아두이노와 `ros2_control_node`로 로드, 활성화, 명령·상태 왕복, `inactive ↔ active` 전환을 확인했다.
- **v5에서는.** 통신은 pi3hat(SPI → CAN, IMU 내장)과 moteus 6대다(ros2_ws README 3절 `wbr_hardware`, 4.1절, 4.2절). 출발점은 mjbots의 `pi3hat_moteus_transport.h`와 `moteus.h`다. CAN 버스는 왼쪽 다리 JC1, 오른쪽 다리 JC4, power dist JC3이다(정해졌다, README 2절 11-14).
- **11장의 틀이 그대로 쓰이는 곳.** 같은 이름의 함수를 같은 자리에 쓴다.
  - `on_init`: URDF의 `<param>`으로 설정을 받는다. `HardwareInfo`의 `hardware_parameters`(키-값 쌍)가 11장의 `port`가 들어오는 곳이다. 어떤 설정을 어떻게 줄지(CAN ID, 설정 파일 경로 등)는 README에 적히지 않았다. 설정은 "설정 파일에서 읽게 한다(제안)"까지다(2절 pi3hat 대기 값).
  - `on_configure`: 통신을 연다. 단, v5는 열기 전에 순서가 있다. 질의만 보내고 → hip·무릎에 `MakeOutputNearest` → `home_state`가 2인지 확인 → 토크 명령(ros2_ws README 4.1절 4번). 이 순서를 `on_configure`/`on_activate` 중 어디에 두는지는 README에 적히지 않았다(정할 것).
  - `read()`/`write()`: 블로킹하지 않는다는 원칙이 같다. v5는 `write()`에서 `Cycle`을 시작하고 다음 `read()`에서 거둔다(4.2절 9번). 그래서 **한 주기 지연**이 생긴다(5.4절). 응답은 출처 ID로 짝지으며 응답이 빠진 관절은 NaN으로 두거나 표본 시각을 갱신하지 않는다(4.2절 6, 7번).
  - 비활성화 때 안전 상태(2.8).
- **달라지는 것.**
  - 속도 PID가 아두이노에 있던 것과 달리 토크 명령의 모양을 플러그인이 만든다: `position = NaN`, `velocity = 0`, `feedforward_torque = τ`, `kp_scale = 0`, `kd_scale = 0`, `maximum_torque`, 유한한 `watchdog_timeout`(4.1절 1, 2번). NaN은 "시간 초과 없음"이라 넣지 않는다.
  - **이름으로 접근하는 함수의 실시간 경고.** 11장은 `set_state("wheel_left_joint/velocity", v)`처럼 이름으로 접근한다(공식 예제 `example_2`도 같다). 설치된 `hardware_component_interface.hpp`는 이름 기반 `set_state`/`get_state`/`set_command`/`get_command`에 "not real-time safe"라고 적는다. 11장은 100 Hz에서 문제없이 돌았지만 걸린 시간을 측정하지 않았고, 1 kHz에서도 괜찮은지는 확인하지 못했다. 같은 헤더에 핸들을 직접 받는 오버로드(`set_state(handle, value, wait_until_set)`, `get_state(handle, state, wait_until_get)`, `set_command(...)`, `get_command(...)`)와 공개 함수 `get_state_interface_handle()`, `get_command_interface_handle()`이 있다. 헤더는 이 오버로드도 `wait_until_set = true`(읽기는 `wait_until_get = true`)로 쓰면 실시간 안전하지 않다고 적는다. 이름 기반 함수는 이 값을 `true`로 부른다. 11장도 같은 설명을 하고, 빠른 루프에서는 핸들을 미리 가져다 두고 락을 기다리지 않는 호출(`wait_until_* = false`)을 쓰는 식으로 달리 해야 한다고 적는다.
  - **루트 권한과 한 번에 한 프로그램.** pi3hat은 root로 돌고, `ros2_control_node`가 떠 있으면 `tview`, `pi3hat_tool`, `moteus_tool`을 못 쓴다(4.2절 1번). root 노드와 일반 사용자 노드는 FastDDS 공유 메모리로 통신하지 못하므로 같은 UDP 프로필을 준다(4.4절 8번, `wbr_bringup`의 `fastdds_udp.xml`).
  - 라이브러리는 `third_party` 복사 대신 `FetchContent`(커밋 고정)가 제안이다(3절 `[수정]`). 11장의 `libserial-dev`처럼 시스템 패키지를 쓰는 방식과 다르다.
- **정할 것.** moteus 시간 초과 동작(4.1절 5번, 7절), 새 IMU 표본이 없는 주기의 처리(4.2절 4번), `wait_for_attitude`를 쓸지.
- **참고할 곳.** 11장, 12장, `ros2_control_demos` 예제 2(Jazzy 방식의 `diffbot_system.hpp`, 10장 단계 2가 가리킨 파일). pi3hat 인터페이스 세 개(`pi3hat_hw_bartlomiej`, `pi3hat_robotic_systems`, `pi3hat_hw_glevine`)는 Humble API이고 일부는 라이선스 때문에 **읽기만** 한다(references README 표, ros2_ws README 1절 (d)). 이 가이드는 읽어 보지 않았다.

### 2.6 제어 주기와 실시간

- **bumperbot에서는.** `update_rate: 100`(03장). `/joint_states`가 약 100 Hz로 나오는 것을 확인했다. 12장의 실물 구성 시험에서 `ros2_control_node`를 일반 사용자로 띄우자 `Could not enable FIFO RT scheduling policy ... Operation not permitted` 경고가 나왔다(12장 단계 3의 로그 설명에 있다). 12장은 실시간 스케줄링 권한이 없는 일반 환경에서 나오는 경고이고 시험에 영향이 없다고 적는다. 경고 문구는 실시간 스케줄링을 켜는 방법이 적힌 control.ros.org 문서를 가리킨다.
- **v5에서는.** 제어 주기 목표는 **1 kHz**이고 파라미터로 둔다. Pi에서 안 나오면 500 / 200 Hz로 내린다(정해졌다, 실측 뒤 확정, ros2_ws README 2절, 6절 C4). Pi에는 실시간 커널과 `isolcpus`를 쓴다(6절 B1). 한 틱의 최대 시간(후보 300 µs 이하, B3)과 센서 → 토크 지연(후보 8 ms 이하, C6)은 아직 측정 전이다.
- **새로 배울 것.**
  - 주기가 하나가 아니다. 설치된 헤더에서 CM의 `update_rate`, 제어기마다의 `get_update_rate()`, 하드웨어 컴포넌트마다의 `rw_rate`와 `is_async`(`HardwareInfo`)가 확인된다. URDF의 어느 속성으로 주는지는 확인하지 못했다(라이브러리 문자열에 `rw_rate`, `is_async`, `scheduling_policy`가 있다).
  - 실시간 스케줄링을 켜는 방법. 저장소 문서에는 없지만 일반 지식에 따르면 이 정책에는 권한이 필요하다. 위 경고가 가리키는 control.ros.org 문서를 보라.
  - 물리 스텝과 CM 주기의 관계(2.4).
- **이 가이드가 보여 준 것은 100 Hz뿐이다.** 1 kHz에서의 동작, 지터, 계산 시간은 확인하지 못했다.

### 2.7 launch 전환: `is_sim` ↔ `hw_env`

- **bumperbot에서는.** xacro 인자 `is_sim`(참·거짓)이 `bumperbot_ros2_control.xacro`의 `<hardware>`만 가른다(12장). launch는 구성마다 다르다: 시뮬레이션은 `gazebo.launch.py`, 실물은 `hardware_interface.launch.py`(`robot_state_publisher`와 `ros2_control_node`). `bumperbot_bringup`의 launch 둘이 그것들을 묶는다(12장).
- **v5에서는.** `hw_env = real | mujoco | gazebo` 하나로 갈린다. `wbr_description`의 `ros2_control.xacro`와 `wbr_bringup`의 `robot.launch.py`가 맡는다(ros2_ws README 3절). 정해진 것은 이름과 세 값이고 세부는 아직 없다.
- **새로 배울 것.**
  - 참·거짓 분기를 세 갈래로 늘리는 xacro 문법. 이 가이드는 `xacro:if`/`unless`의 참·거짓만 다뤘다.
  - launch의 인자를 xacro의 인자로 넘기는 일(참조 Section12의 `hardware_interface.launch.py`는 `Command(["xacro ", ..., " is_sim:=False"])` 모양이다).
  - 제어기 파라미터를 CM에 주는 길. ros2_ws README 1절 (d)는 Jazzy에서 제어기 파라미터를 스포너의 `--param-file`로 넘긴다고 적는다(DDT 코드가 Humble 방식이라는 맥락). 이 가이드의 방식은 하나 더 있다. CM에 준 yaml 하나로 모든 제어기의 파라미터가 적용되고 스포너에 `--param-file`을 주지 않는다. 시뮬레이션(03장)과 실물 `ros2_control_node`(12장 단계 4) 모두에서 확인했다. CM 로그에 `Controller 'bumperbot_controller' node arguments: --ros-args --params-file <그 yaml>`이 나오고 `ros2 param get /bumperbot_controller wheel_radius`가 yaml의 값(0.033)을 돌려줬다. 스포너의 `--param-file`은 한 제어기에만 다른 파일을 더 적용할 때 쓰는 선택 사항이다. 어느 방식을 쓸지는 정할 것이다.
  - 파라미터 yaml을 사람이 아니라 스크립트가 만든다는 점. `export_params.py`가 `wbr_params_<주기>hz_<이름>.yaml`을 만들고 손으로 옮기지 않는다(ros2_ws README 3절, 5.1절).
- **참고할 곳.** `ros2_control_demos` 예제 9, 12장(특히 단계 1의 `is_sim`·`port`, 단계 3의 `hardware_interface.launch.py`, 단계 6의 두 bringup launch).

### 2.8 안전: 끌 때와 죽었을 때

- **bumperbot에서는 층이 셋이고 하나는 비어 있다.**
  - 제어기 층: `diff_drive_controller`는 `cmd_vel_timeout` 0.5초 뒤 정지한다(05장). `JointGroupVelocityController`는 마지막 명령을 유지한다(03장).
  - 플러그인 층: `on_deactivate`가 `rp00.00,lp00.00,` 정지 명령을 보낸다(11장). 12장 단계 5에서 달리는 중에 하드웨어를 `inactive`로 내리면 정지 명령이 나가고, `diff_drive_controller`는 `active`로 남으며, `/joint_states`는 계속 나오는 것을 확인했다. `active`로 되돌리면 제어기가 쓰던 명령이 곧바로 다시 나간다. `ros2_control_node`를 끌 때도 `deactivate` 뒤에 `shutdown`이 불리고 정지 명령이 간다.
  - 장치 층: 아두이노 스케치에 시간 초과(워치독)가 없다(11장). 플러그인이 죽으면 마지막 명령으로 계속 돈다.
- **v5에서는 세 층 모두 정해야 한다.**
  - 명령이 0.5 s 넘게 끊기면 전진·요는 0이 되고 균형은 계속한다(ros2_ws README 4.4절 2번).
  - 피치·롤 34° 초과 등이면 FAULT이고 모든 관절 토크 0이다(4.4절 4번).
  - 제어기를 끌 때 `on_deactivate`에서 토크 0을 쓴다. ros2_control은 마지막 명령 값을 지우지 않는다(4.4절 5번). 이것은 03장에서 본 현상(퍼블리셔를 껐는데 바퀴가 계속 돈다)의 일반화다. 플러그인은 effort를 잡은 제어기가 없어지면 `stop`을 보낸다(같은 항목).
  - Ctrl+C로 끄면 플러그인이 모든 관절에 `stop`을 보낸다. 프로그램이 죽으면 moteus의 시간 초과가 맡는다(4.4절 6번, 4.1절 5번). `watchdog_timeout`은 유한한 값이다(4.1절 2번).
- **새로 배울 것.** 어느 층이 무엇을 책임지는지 나누는 일. "effort를 잡은 제어기가 없어지면 stop"을 플러그인이 어떻게 알 수 있는지는 확인하지 못했다. 11장 단계 6의 표에서 "쓰지 않음"으로 지나간 `prepare_command_mode_switch`/`perform_command_mode_switch`(제어기를 바꿔 끼울 때 불린다)가 후보로 보이지만 이 가이드에서 시험하지 않았다.
- **정할 것.** moteus 시간 초과 동작, fault에서 나가는 방법, arm / disarm 수단(4.1절 5번, 4.4절 3번, 7절).
- **참고할 곳.** 03장 단계 6의 "멈추려면 `[0.0, 0.0]`", 11장 단계 8~9, 12장 단계 5, ros2_ws README 4.4절. README는 `template_ros2_controller` 등에 안전 검사와 명령 타임아웃이 없으므로 4.4절을 반드시 넣으라고 한다(6절 A5).

## 4. 이 가이드로 답할 수 있게 된 질문, 아직 못 하는 것

### 답할 수 있게 된 질문

- ros2_control에서 제어기와 하드웨어가 어떻게 나뉘고 무엇으로 연결되는가(00장, 03장).
- 쓰려면 어떤 파일이 필요하고, 없으면 어떤 증상이 나는가(00장 4절).
- 패키지를 왜 description / controller / firmware / bringup으로 나누는가, `package.xml`과 `CMakeLists.txt`는 각각 누가 읽는가(00장 5절, 01·02장).
- 표준 제어기를 yaml 설정만으로 올리고 `ros2 control` 명령으로 상태·점유를 확인하는 법(03장, 05장).
- 하드웨어 컴포넌트 플러그인의 골격: `on_init`에서 URDF 읽기, 생명주기 콜백, `read`/`write`, pluginlib 등록(10장, 11장).
- 그 플러그인을 URDF에 연결하고 `ros2_control_node`로 띄우고 제어기를 올리는 법, 하드웨어를 손으로 `inactive`로 내렸을 때 무슨 일이 일어나는가(12장).
- 시뮬레이션과 실물을 어디서 갈라 쓰는가(03장 단계 8, 12장).

### 아직 못 하는 것

- **제어기 플러그인을 쓰는 것.** 이 가이드에 없다. 2.3의 자료로 직접 배워야 한다.
- **effort 명령, 6조인트 URDF.** 모양만 보였고 돌려 보지 않았다(2.1).
- **`<sensor>`, `<gpio>`, 추가 state interface로 IMU와 드라이버 상태를 올리는 것.** 헤더와 예제를 가리켰을 뿐 시험하지 않았다(2.2).
- **MuJoCo 시뮬레이션.** `mujoco_ros2_control`이 이 노트북에 설치돼 있지 않다(2.4).
- **pi3hat, moteus, CAN, root 실행, FastDDS 설정.** 11장과 12장은 시리얼 포트(가상)와 가짜 아두이노로만 시험했다(2.5).
- **1 kHz와 실시간.** 100 Hz만 돌려 봤다. 실시간 스케줄링, 지터, 계산 시간은 확인하지 못했다(2.6).
- **체인형 제어기 작성, 비동기(`is_async`) 하드웨어·제어기.** 헤더에 있는 것을 가리킨 것뿐이다.
- **v5의 안전 동작 전체**(2.8). bumperbot의 정지 처리는 한 층씩만 다뤘다.
- **정할 것은 정하지 않았다.** README 7절의 목록이 기준이다. 이 장은 그중 ros2_control 구조와 맞닿은 것(인터페이스 이름, 상태 기계의 위치, moteus 시간 초과, 설정 전달)만 가리켰다.
